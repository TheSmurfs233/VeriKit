# 03 阶段推进与验收

> 阶段划分决定项目能不能"稳步推进"。
> 划分得好：每个阶段失败都是局部的、可归因的；
> 划分得差：一个失败就要推翻重来。

---

## 1. 好阶段的四个特征

| 特征 | 检验方法 |
|---|---|
| **产出一种可独立验证的能力** | 能用一句话说清"它能干什么" |
| **验收标准可量化** | 有数值阈值或明确的通过/失败判据 |
| **失败是局部的** | 这个阶段失败，之前的成果依然有效 |
| **1~5 天可完成** | 超过就再拆一层 |

---

## 2. 阶段拆分方法

### 2.1 按"能力链"拆，不按"代码模块"拆

❌ 错误：按代码目录拆（"先写 `src/core`，再写 `src/vscode`"）
—— 无法验证，因为每层单独都没法证明"对了"

✅ 正确：按能力拆（"能着色" → "着得准" → "能靠它做导航"）
—— 每步都有可观测的产出

### 2.2 "能做" 与 "做得对" 必须分开

这是本流程最关键的拆分技巧：

| 阶段类型 | 产出 | 验证方式 |
|---|---|---|
| **能力阶段** | 功能"能跑起来" | 有没有输出、有没有动作 |
| **精度阶段** | 功能"跑得准" | 误差指标、覆盖率、边界表现 |

例：

```
S3a 索引能建起来（能跑）      → 验证：打开工程后模块列表非空，且包含全部 module
S3b 索引准（准不准）          → 验证：模块树与 `grep -r "^module"` 的结果一致
S3c 例化输出正确（准不准）    → 验证：与手写基准逐字节相等
```

**好处**：如果 S3b 不达标，你知道问题在"索引精度"而不是"解析器没接上"。

### 2.3 影子模式（Preview Mode）原则

任何**会改变用户文件的动作**，先以"只算/只展示"的方式运行，与预期对比，达标后再接入写入。

```
阶段 1：只生成预览，不落盘（影）        —— 用户看得见，但 Ctrl+Z 都不需要
阶段 2：预览与手写基准对比，逐字节相等（验）
阶段 3：开启"确认后写入"（切）          —— 走 WorkspaceEdit，可撤销
阶段 4：保留预览开关，可随时回退（留）  —— 配置项 verikit.insert.preview = true
```

**收益**：新功能永远不会"直接把用户的代码写坏"，且开启写入有据可依。

典型应用：一键例化、格式化、批量重命名。**这三者都应先做预览模式。**

---

## 3. 阶段文档（开工前必须写）

每个阶段开工前，写一份 `templates/t_阶段方案.md`，包含五节：

```markdown
## S<n> <阶段名>

### 1. 目标（可验证）
- 能 <做什么>，验收标准：<可量化>

### 2. 非目标（本阶段不做）
- <明确排除>

### 3. 技术路线
<怎么做；若有备选，写明为什么选这条>

### 4. 验证方法
<哪一级测试（L1~L4）证明它成了；用什么样本/命令>

### 5. 风险与对策
| 风险 | 影响 | 对策 |
```

> **不写方案的阶段不允许开工**。
> 方案的价值不在于"正确"，而在于逼你想清楚"怎么证明它成了"。

---

## 4. 验收标准怎么写

### 4.1 五种合格的验收标准

| 形式 | 示例 |
|---|---|
| **正确率** | 模块树与 `grep` 结果一致率 100%（42/42 个 module） |
| **相等性** | 诊断集合 == CLI 独立输出的集合（条数、行、列、级别全等） |
| **精度** | 一键例化的输出与手写基准逐字节相等 |
| **阈值** | 248 行文件的单次诊断耗时 < 300 ms；插件激活耗时 < 200 ms |
| **行为** | 工具链缺失时，诊断整簇清空且状态栏显示原因（**不留旧红线**） |

第五类"**行为型判据**"在插件项目里特别重要，因为它往往是最容易被忽略的降级路径。

### 4.2 不合格的写法

| ❌ 写法 | 问题 |
|---|---|
| "运行正常" | 无法判定 |
| "高亮效果不错" | 无阈值、无基准 |
| "支持了 xx 语法" | 支持到哪一步？哪些不支持？ |
| "基本可用" | 不可验证 |

### 4.3 验收标准要写"如何测"

```markdown
| 项 | 标准 | 测法 |
|---|---|---|
| 诊断完整性 | 与 CLI 输出 100% 相等 | `node test/golden/run.js --only broken_syntax`，比对 23 条 |
| 高亮回归 | 无意外 scope 变动 | 改 grammar 后跑全量 corpus，diff 必须可解释 |
| 降级行为 | 整簇清空 | 把 `verikit.toolchain` 设为 `none`，观察诊断面板清空 + 状态栏提示 |
```

---

## 5. 验收执行规范

### 5.1 用脚本，不用手

每个阶段配一个可重复运行的验收入口，要求：

- 参数化（样本集、容差、只跑某个子集）
- 输出**结构化结果**（PASS/FAIL + 实测值）
- 可重复运行（不依赖上次状态：开始前先清理临时目录与诊断集合）
- 失败时打印**当时的完整上下文**（不只是"失败"）

```bash
# 结构示意
node test/golden/run.js --only broken_syntax --verbose
# 输出
# [case] broken_syntax.v
#   expected 23 diags, actual 11
#   missing: L14 W, L15 W, ... (12 条)
#   RESULT: FAIL
```

### 5.2 记录"失败那一次"的数据

失败是随机的（竞态、首次加载、缓存），所以**必须在失败发生的那一刻抓状态**，
而不是事后复盘（事后状态已经变了）。

做法：脚本在判断失败时，立刻 dump 全部相关上下文 —— 文档 `languageId`、
工具链配置与实际绝对路径、命令行 argv、退出码、原始 stdout/stderr 字节数、
解析出的诊断条数、请求序号。

**这就是 `VeriKit: 导出诊断 JSON` 命令存在的理由**（见 `07` §4）。

### 5.3 验收通过后必做三件事

1. 数据写入 `00_开发日志`（含日期、版本 build 号、测试环境）
2. `01_项目进度` 更新状态 + 证据
3. 相关架构文档补充"新发现的坑"

---

## 6. 阶段的"回退"规则

情况：阶段 N 进行中发现阶段 N-2 有缺陷。

**正确做法**：
1. 在 `00` 记录发现的问题与证据
2. 在 `01` 把阶段 N-2 改回 `🟡 进行中`，写明原因
3. 修好 N-2 并重新验收
4. 再回到 N

**错误做法**：在阶段 N 里"顺手绕过"——这会让 N 的结论建立在错误前提上。

> 插件项目里最常见的越界：**在实现诊断功能时，顺手去修 grammar 的着色问题**。
> 两者毫不相干，混在一个提交里，出问题时无法归因。

---

## 7. 一个完整阶段的生命周期（示例）

```markdown
## S4 诊断层（语法检查）

**方案**（提前写）
- 目标：插件诊断集合与 CLI 独立输出 100% 相等（条数/行/列/级别）
- 非目标：不处理 SystemVerilog 独有语法；不做 quick fix
- 路线：`ProcessRunner` 调用户配置的工具链 → 归一化 → 单一 owner 写入
- 验证：golden corpus 全量比对；降级行为手验

**实施**
- 加 `core/diag/normalize.ts` 与 `DiagnosticManager`；v0.4.0 build 35
- 初版正则只匹配首行（后来证明是错的，见下）

**验收（第一次）**
| 项 | 标准 | 实测 | 结论 |
|---|---|---|---|
| 诊断完整性 | 与 CLI 100% 相等 | 11/23 | ❌ |
| 耗时 | < 300 ms | 92 ms | ✅ |
| 降级行为 | 整簇清空 | 通过 | ✅ |

**归因（关键步骤）**
- 缺的 12 条全部是 warning
- 打印原始输出发现：xvlog 的 warning 是**两行**（首行给位置，次行给上下文）
- 查代码：解析器用 `/^(ERROR|WARNING):(.*)/` 逐行匹配，次行没有前缀 → 被丢弃
- **结论：解析器对"多行诊断"的假设错了**（与工具链无关）

**修复 + 二次验收**
- 改为按"位置行"聚合，后续行并入上一条，v0.4.1 build 37
- 实测 23/23 ✅

**沉淀**
- `07_调试方法论` 新增案例："不用被验证对象验证自己"
- `00` 记录两次验收数据与推翻过程
- 新增回归断言 `xvlog 多行诊断不丢失`
- `01` 标记 S4 ✅，证据：23/23，build 37
```

**注意**：这次"失败 → 归因 → 修复"的过程本身，
比"一次通过"更有价值 —— 它产出了可复用的方法论。
