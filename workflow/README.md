# 软件开发流程规范（可复用）

> 本文件夹原为嵌入式固件项目（STM32 + FOC）的流程，现已改造为**通用软件开发流程**，
> 并以 **VSCode 插件开发（TypeScript / Node）** 作为默认落地场景。
>
> 与语言、平台无关的部分（阶段、门禁、文档体系、判据设计）原样保留；
> 与领域绑定的部分（仿真、硬件、案例）已替换为软件工程等价物。
>
> 目标：让"一个人 + AI 协作"的项目也能做到
> **每一步有方案、每一改有测试、每一个数字有出处、每一份文档不过期**。

---

## 1. 这套流程解决什么问题

| 常见问题 | 本流程的对策 |
|---|---|
| 改完就 F5，看着能跑就提交 | 三方验证门禁（静态检查 / 自动化测试 / 文档检查） |
| 现象时好时坏，越改越乱 | 调试方法论：先测量、后假设、对照实验 |
| 文档写着旧结论，代码早已改掉 | 文档检查脚本 + 版本号绑定 + 关键清单自动生成 |
| 需求一多就不知道做到哪了 | 阶段化推进 + 进度表 + 验收标准 |
| 同一类 bug 反复出现 | 症状-根因对照表 + 回归断言 |
| 换个工程又要重新摸索 | 本文件夹整套复制，改 5 处即可 |

## 2. 十条硬规则（TL;DR）

1. **先方案，后动手**：任何非平凡改动先出方案，评审通过再执行。
2. **先测试，后实现**：新增/修改的逻辑，先写一条能**失败**它的测试。
3. **一阶段一验收**：阶段不通过不进下一阶段，不跳步。
4. **三方验证才提交**：静态检查 0 错 0 警 + 测试全过 + 文档检查 PASS。
5. **每次可安装的改动都递增版本号**，文档里写的版本必须与代码一致。
6. **判据要用不变量**，不能用"看着对"（血的教训，见 `07`）。
7. **状态切换必须有硬优先级**，不能只靠标志位、更不能靠"谁后跑谁赢"。
8. **先测量再修改**：没有数据支撑的修改都是猜测。
9. **依赖缺失必须优雅降级，不许吞异常伪装成功**（显示"0 个问题"比报错更危险）。
10. **外部动作先请示**：启动子进程、写用户文件、改用户配置、联网下载都要先确认。

## 3. 目录结构

```
workflow/
├── README.md                  ← 本文件：总览与使用方法
├── 01_开发流程总纲.md          ← 五个阶段与五个门禁
├── 02_文档体系规范.md          ← 必备文档清单、编号、写作规则、自动生成
├── 03_阶段推进与验收.md        ← 阶段拆分方法、验收标准模板、影子模式
├── 04_测试先行.md              ← 四级测试金字塔：单元 / 快照 / 集成 / 手动
├── 05_验证与提交规范.md        ← 三方验证、版本号、提交信息、分支
├── 06_外部依赖与安全.md        ← 授权模型、安全红线、子进程与降级策略
├── 07_调试方法论.md            ← 判据设计、对照实验、症状-根因表
├── 08_新工程落地清单.md        ← 从零搭建时按此清单逐项打钩
└── templates/                 ← 可直接复制的文档模板
    ├── t_开发日志条目.md
    ├── t_进度表.md
    ├── t_框架文档.md
    ├── t_阶段方案.md
    ├── t_阶段验收.md
    └── t_已知问题与限制.md
```

> 六个模板对应三种"必须写"的场景：
> **开工前**写方案（`t_阶段方案`），**过程中**记日志与框架（`t_开发日志条目`、`t_框架文档`），
> **收尾时**做验收与归档（`t_阶段验收`、`t_进度表`、`t_已知问题与限制`）。

## 4. 怎么复用到新工程

### 4.1 复制

把整个 `workflow/` 复制到新工程根目录，然后按下图建目录：

```
新工程/
├── docs/
│   ├── 00_开发日志.md          ← 追加式，永不删旧条目
│   ├── 01_项目进度.md          ← 唯一的"现在做到哪"的事实来源
│   ├── 10_框架_三层架构.md     ← 分层、数据流、进程边界
│   ├── 11_框架_<子系统>.md     ← 一个子系统一份，按 11,12,13… 编号
│   ├── 18_待确认清单.md        ← TBD 与悬案集中营
│   ├── 30_命令手册.md          ← 【自动生成】来自 package.json contributes.commands
│   ├── 31_参数表.md            ← 【自动生成】来自 contributes.configuration
│   ├── 32_调试指南.md          ← 常见现象与排查路径
│   └── 90_已知问题与限制.md
├── test/
│   ├── doc_check.py            ← 文档一致性静态检查
│   ├── unit/                   ← vitest 单元测试
│   ├── golden/                 ← corpus + expected 快照基准
│   └── integration/            ← @vscode/test-electron 集成测试
├── src/
│   ├── core/                   ← ★ 不 import vscode，可离线单测
│   └── vscode/                 ← 适配层：命令、诊断、状态栏
├── verify.sh                   ← 三方验证一条命令
└── workflow/                   ← 本文件夹
```

### 4.2 只改这 5 处

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `test/doc_check.py` | 文档路径、版本号来源（`package.json` / `BUILD_ID`）、`.v` 与 `.json` 的对应关系 |
| 2 | 框架文档编号段 | `10` 主架构，`11+` 子系统；按新工程划分 |
| 3 | `docs/01_项目进度.md` | 阶段划分（S0…Sn）与验收标准 |
| 4 | `05_验证与提交规范.md` §2 | 静态检查命令、测试命令、版本号字段名 |
| 5 | `workflow/templates/` | 模板里的占位符替换为新工程术语 |

其余内容可直接沿用。

## 5. 一个功能从想法到交付的完整轨迹

```
想法
 │
 ├─① 写进 docs/01 的"待做"         ← 需求入库，避免口头遗忘
 │
 ├─② 出方案（templates/t_阶段方案.md）
 │     · 目标 / 非目标
 │     · 技术路线与备选
 │     · 验证方法（怎么证明它成了，哪一级测试）
 │     · 风险与回退
 │     ↓ 评审通过
 │
 ├─③ 测试先行（04_测试先行）
 │     · L1 单元测试 / L2 快照基准 / L3 集成接线
 │     ↓ 先让测试失败，再让它通过
 │
 ├─④ 实现 + 版本号 +1（package.json version 与 BUILD_ID）
 │
 ├─⑤ 三方验证（05_验证与提交规范）
 │     · tsc + eslint 0 错 0 警
 │     · vitest 全过 + 基准无意外变动
 │     · doc_check PASS
 │     ↓ 全过
 │
 ├─⑥ 提交（一次逻辑改动一个提交，信息含"问题/根因/修法/验证"）
 │
 ├─⑦ 手动验收（06_外部依赖与安全：外部动作先请示）
 │     · F5 手动检查清单
 │     · 数据写入 docs/00 开发日志
 │     ↓ 达标
 │
 └─⑧ 更新 docs/01 进度表 + 相关框架文档 → 进入下一个功能
```

**任何一步失败，就回到上一步，不允许"带病前进"。**

## 6. 与"AI 协作"的约定

本流程假设执行者可能是 AI，因此额外要求：

| 约定 | 原因 |
|---|---|
| 方案必须写成文档，不接受口头 | AI 上下文会丢，文档不会 |
| 每个结论必须带数据（数值、日志片段、diff） | 防止"看起来可以了"的幻觉 |
| 修改前必须先读代码/文档 | 防止重复发明、防止覆盖已有修复 |
| 外部动作先请示 | 用户的文件与环境不该被单方面改变 |
| 一次只改一个变量 | 否则失败时无法归因 |
| 假设被推翻时必须显式记录 | 这是最有价值的知识沉淀 |
| 文档与代码不一致时，先改文档再继续 | 否则后续所有推理都建立在错误前提上 |
| **不允许用"我手动点过了，正常"作为通过依据** | 手点结果不可复现、不可检索、不可回归 |

## 7. 本规范的"最小可用版"

如果工程很小（几百行、一次性验证），可只做四条：

1. `docs/00_开发日志.md` + `docs/01_项目进度.md`
2. 每次改动递增版本号，启动时打印一行版本
3. 提交前跑一遍静态检查 + 测试
4. 关键判据用不变量（见 `07`）

其余文档在工程变大、或需要第二个人接手时再补齐。
