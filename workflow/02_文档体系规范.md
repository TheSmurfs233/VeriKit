# 02 文档体系规范

> 文档不是"写给人看的报告"，而是**项目的可执行记忆**。
> 判断一份文档是否合格：**换一个人（或换一个 AI 会话）能否只靠它继续工作。**

---

## 1. 编号规则

采用"十进制分段 + 前缀"，一眼看出文档性质：

| 段 | 用途 | 示例 |
|---|---|---|
| `00~09` | **过程文档**（日志、进度、决策） | `00_开发日志`、`01_项目进度` |
| `10~29` | **架构文档**（分层与子系统） | `10_框架_三层架构`、`13_框架_诊断归一化` |
| `30~39` | **使用文档**（面向操作者） | `30_命令手册`、`31_参数表` |
| `40~59` | **方案与评估**（一次性深度文档） | `43_语法检查方案评估` |
| `90~99` | **遗留与已知问题** | `90_已知问题与限制` |

**规则**：
- 编号只增不改，废弃文档标注"已废弃"但**不删**（历史可追溯）
- 新增文档时接在同类编号末尾，不要插队

## 2. 必备文档清单

### 2.1 核心：五份手写 + 两份自动生成

**项目小的时候最危险的错误，是把文档清单照抄成十六份。** 对插件项目，只需这些：

| 文档 | 方式 | 作用 | 更新频率 |
|---|---|---|---|
| `00_开发日志.md` | 手写 | 时间线事实记录，含**每次实验的数据** | 每次实验 |
| `01_项目进度.md` | 手写 | 唯一"现在做到哪"的事实来源 | 每阶段 |
| `10_框架_三层架构.md` | 手写 | 系统怎么跑起来（分层、数据流、进程边界、时序） | 架构变化时 |
| `18_待确认清单.md` | 手写 | 所有 TBD 与悬案的唯一去处 | 随时 |
| `90_已知问题与限制.md` | 手写 | 已知缺陷、不打算修的问题、规避方法 | 每次发现 |
| `30_命令手册.md` | **自动生成** | 全部命令、参数、行为 | 跟随 `contributes.commands` |
| `31_参数表.md` | **自动生成** | 全部配置项、默认值、范围 | 跟随 `contributes.configuration` |

> **`01_项目进度` 是单一事实来源**。
> 任何"做完了吗"的问题，答案只能在它里面，不能散落在聊天记录里。

### 2.2 按需新建

| 触发条件 | 必须新建的文档 |
|---|---|
| 某个子系统超过 ~500 行，或职责可一句话独立描述 | `11_框架_<子系统>.md` |
| 进入需要反复试错的阶段 | `32_调试指南.md` |
| 做出重要技术选型（选 A 不选 B） | `4x_方案_<主题>.md` + `00` 的决策记录 |
| 交付给他人使用 | `37_使用指南.md`（分步骤、含期望输出） |

### 2.3 为什么命令手册与参数表不手写

在插件项目里，**命令清单和配置项本身就是代码**：

```jsonc
// package.json —— 这是唯一的真相来源
{
  "contributes": {
    "commands": [{ "command": "verikit.showDiagnostics", "title": "显示诊断信息" }],
    "configuration": { "properties": { "verikit.toolchain": { "type": "string" } } }
  }
}
```

手写一份 `30_命令手册.md`，等于把同一份信息维护两次。第一次改动就会失同步，
而**过期的命令文档比没有文档更危险**（会引导人用不存在的命令）。

做法：`test/gen_docs.py` 从 `package.json` 生成两张表，`doc_check.py` 检查生成结果是否为最新。

## 3. 每类文档的写法

### 3.1 开发日志（`00`）

**唯一规则：追加，不改旧条目。**

每条包含：

```markdown
## YYYY-MM-DD · <一句话主题>

### 背景 / 问题
<现象、触发条件、当时在做什么>

### 数据
| 项 | 值 | 来源 |
|---|---|---|
<必须是实测值，不是估计>

### 分析
<推理链：从数据到结论>

### 结论与动作
<改了什么、为什么这样改>

### 验证
| 项 | 结果 |
|---|---|
```

**禁忌**：
- ❌ "优化了一下性能"（无法复现）
- ✅ "单文件诊断耗时 480 ms → 92 ms（`exportDiag` 实测，248 行文件），因为把 `spawn` 从每次按键触发改成 300 ms 防抖 + 增量文件列表"

### 3.2 进度表（`01`）

**一行一个阶段**，列固定的五列：

```markdown
| 阶段 | 名称 | 状态 | 验收标准 | 证据/版本 |
|---|---|---|---|---|
| S4 | 诊断层 | ✅ 完成 | 诊断集合与 CLI 输出 100% 相等 | 23/23，v0.4.1 build 37 |
```

**状态取值只允许五种**：`⬜ 未开始`、`🟡 进行中`、`✅ 完成`、`⚠️ 完成但有保留`、`❌ 放弃（原因）`

**禁忌**：不要写"基本完成""差不多好了"。要么达标，要么没达标。

### 3.3 架构文档（`10`~`2x`）

固定七节结构（模板见 `templates/t_框架文档.md`）：

1. **职责**：这个模块负责什么、不负责什么
2. **接口**：对外函数 / 命令 / 配置
3. **数据结构**：关键结构体与状态机
4. **运行上下文**：在扩展宿主（单线程事件循环）还是独立进程里跑，触发时机，耗时
5. **算法/流程**：核心逻辑与数据流
6. **参数**：可调项、默认值、取值范围、影响
7. **坑与注意事项**：踩过的坑（这一节最有价值）

### 3.4 命令手册（`30`，自动生成）

必须包含：
- 完整命令列表（**与 `contributes.commands` 条数相等**，脚本校验）
- 每条命令的参数、取值范围、返回示例
- 错误提示 / 降级行为对照表

### 3.5 参数表（`31`，自动生成）

必须包含：配置键、含义、**类型与单位**、默认值、范围、影响面、修改后是否需要重启窗口。

> 单位必须写。同一个量在不同层用不同单位（如 `ms` / `s`、`bytes` / `chars`）
> 是软件项目最常见的 bug 来源之一。

### 3.6 已知问题（`90`）

| 编号 | 现象 | 影响 | 触发条件 | 规避方法 | 状态 |
|---|---|---|---|---|---|

**"不打算修"的问题也必须写进去**，并写明理由。
插件类项目建议再加一类：**平台差异**（Windows / macOS / Linux 各自的行为差异）。

## 4. 写作硬规则

| 规则 | 说明 |
|---|---|
| **数字优先** | 每个结论附数值 / 日志片段；禁止"更快""更稳"这类形容词 |
| **单位必写** | `92 ms` 而不是 `92`；`bytes` 与 `chars` 不能混 |
| **路径写全** | 涉及文件时写相对路径或模块名，不写"那个配置文件" |
| **表格列数一致** | 用 `doc_check.py` 自动检查（否则渲染错乱） |
| **相对路径引用** | 文档之间用相对路径互链，避免工程搬家失效 |
| **TBD 集中** | 所有未定项进 `18_待确认清单`，正文不留 `TBD`（脚本扫描） |
| **不复制，只引用** | 参数只在 `31_参数表` 出现一次，其他地方用链接 |

## 5. 文档检查自动化（`doc_check.py`）

文档一旦超过 10 份，人工核对必然失守。用脚本守六条底线：

### 5.1 检查项

| 检查 | 目的 |
|---|---|
| **版本号一致性** | `docs/01` 里写的版本 == `package.json` 的 `version` == 代码里的 `BUILD_ID` |
| 表格列数一致性 | 防止渲染错乱、防止"看起来有内容其实错位" |
| **命令数 / 配置数一致** | `contributes.commands` 条数 == 生成的 `30_命令手册` 条目数 |
| **corpus 与 expected 一一对应** | 每个 `*.v` 必须有同名基准 `*.json`（插件域特有） |
| TBD 残留扫描 | 正文里的未定项必须收敛到 `18_待确认清单` |
| 编码异常字符 | 防止编辑器把中文写成控制字符，或写出替换字符 U+FFFD |

### 5.2 版本号一致性的重要性

这是**投入产出比最高的一条**：

```
package.json 里 version = 0.4.1，BUILD_ID = 37
docs/01 里写 "v0.4.0 build 36"       → 立刻报错
```

它保证了"文档描述的行为"与"实际装在你 VSCode 里的插件"是同一版本。
没有这条，你会花大量时间怀疑"是不是没重新加载窗口"。

### 5.3 为什么要有 corpus/expected 对应检查

```
test/golden/corpus/new_case.v     ← 新增了样本
test/golden/expected/new_case.json ← 忘了（或不知道要）生成基准
```

跑测试时这个样本会被**静默跳过**，报告依然全绿。这比没有样本更糟。
脚本必须直接报错。

### 5.4 实现要点（伪代码）

```python
errors = []

# 1) 版本号三方一致
pkg   = json.load(open('package.json'))
ver   = pkg['version']
build = re.search(r"BUILD_ID\s*=\s*(\d+)", read('src/core/version.ts')).group(1)
for doc in ('docs/01_项目进度.md', 'docs/90_已知问题与限制.md'):
    for m in re.finditer(r'build (\d+)', read(doc)):
        if m.group(1) != build:
            errors.append(f'{doc}: build {m.group(1)} != 代码 {build}')

# 2) 表格列数
for doc in glob('docs/*.md'):
    ...  与表头比较，报具体行号 ...

# 3) 命令数
n_cmd = len(pkg['contributes']['commands'])
n_doc = count_table_rows('docs/30_命令手册.md')
if n_cmd != n_doc: errors.append(f'命令数 {n_cmd} != 文档 {n_doc}')

# 4) corpus / expected 对应
for v in glob('test/golden/corpus/*.v'):
    if not exists(v.replace('corpus', 'expected').replace('.v', '.json')):
        errors.append(f'{v}: 缺少基准文件')

# 5) TBD 残留（跳过 00 与 18）
```

> 表格里的 `|` 必须写成 `\|`，否则列数统计会错 —— 这是最容易踩的坑，
> 脚本要能报出具体行号。

## 6. 文档的"过期"治理

文档过期比没有文档更危险（会误导后来的推理）。治理方法：

| 手段 | 说明 |
|---|---|
| 版本号绑定 | 版本一变，所有写死旧版本号的地方立刻报错 |
| **能生成的绝不手写** | 命令手册、参数表从 `package.json` 生成 |
| 每阶段结束 `grep` 一次 | 搜索旧命令名、旧配置键、旧默认值 |
| 决策记录保留 | 被推翻的结论**不删**，标注"已推翻，原因：…" |
| 引用而非复制 | 关键事实只写一次，其他地方用链接 |

---

## 7. 最少工作量的合规做法

时间紧张时，按此优先级保底：

1. `01_项目进度` 必须准确（否则不知道做到哪）
2. `00_开发日志` 每次实验一条（哪怕只写数据表）
3. `31_参数表` 与代码同步（自动生成等于零成本）
4. `90_已知问题` 至少记录"会咬人的"几条
5. `doc_check.py` 只保版本号一致性与 corpus 对应这两条
