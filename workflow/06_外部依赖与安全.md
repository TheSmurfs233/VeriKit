# 06 外部依赖与安全约定

> 插件代码可以回滚，但**用户的工作区不能**。
> 被格式化覆盖掉的代码、被例化插入改乱的模块、被悄悄改掉的 VSCode 配置、下载到一半的二进制 —— 这些都不会自己回来。
>
> 本章定义的是一套明确的**授权边界与红线**，适用于任何"会触碰用户环境"的软件。

---

## 1. 授权模型

### 1.1 必须先请示的动作

| 动作 | 为什么 |
|---|---|
| **启动外部进程**（xvlog / vsim / vivado / formatter） | 会占用 CPU 与内存，可能长时间运行，可能写文件；且会与用户自己的终端冲突 |
| **写入用户工作区文件**（例化插入、格式化写盘、批量替换） | 直接改动用户的源码，覆盖即丢失 |
| **修改用户配置**（`.vscode/settings.json`、全局 settings） | 用户的偏好被静默改变，且很难察觉 |
| **联网下载或执行远程二进制**（formatter、language server） | 供应链风险，且可能下载到不适合当前平台的文件 |
| 安装 / 卸载扩展依赖 | 改变用户环境 |

### 1.2 可以直接做的动作

- 读代码、读文档、写文档
- 修改插件自身源码（不安装、不打包发布）
- 跑单元测试、快照比对、`tsc --noEmit`、`eslint`
- 在系统临时目录（`os.tmpdir()`）写临时文件
- 打开只读的预览视图（不写盘）

### 1.3 冲突处理

外部进程或端口被占用时：
- **不要**尝试强制结束用户的进程
- 告知用户"目标被占用，请关闭后重试"，并在日志里给出**被占用的具体对象**
- 或者提供"导出命令让用户自己跑"的路径（`VeriKit: 复制诊断命令`）

## 2. 安全红线（永远不做）

| # | 红线 | 原因 |
|---|---|---|
| 1 | **不静默写用户文件** | 格式化 / 例化必须**先出 diff 预览**，用户确认后才落盘 |
| 2 | **不静默修改用户配置** | 需要改 settings 时，弹窗说明改什么、为什么，并给"拒绝"选项 |
| 3 | **不静默下载并执行远程二进制** | 供应链攻击面；确需下载时必须由用户显式确认且展示 URL 与校验值 |
| 4 | **不吞异常伪装成功** | 工具链缺失时显示"0 个问题"，比报错更危险 —— 用户会以为代码是对的 |
| 5 | **不在用户工程目录留临时文件** | 一律用 `os.tmpdir()`，且进程结束后清理 |
| 6 | **不在扩展宿主里做同步阻塞** | 一个 `execSync` 就能让整个 VSCode 卡死（用户会以为 VSCode 崩了） |
| 7 | **不用 `shell: true` 拼命令字符串** | 路径里的空格、`&`、`|`、中文引号都会变成命令注入或解析错误 |
| 8 | **不覆盖用户已有的非本插件配置** | 合并而非替换；删除时只删自己加的键 |

### 2.1 第 6 条的量化说明

VSCode 的扩展宿主是单线程事件循环。任何一次同步文件 I/O 或 `execSync`，都会阻塞**所有**扩展的 UI 响应。

```
一次 xvlog 调用 300 ms（大工程可能 5 s）
→ 同步执行 = 界面卡 300 ms~5 s
→ 用户看到的是"编辑器假死"
```

**要求**：所有外部进程必须走异步 API（`child_process.spawn`），并支持 **取消**（`CancellationToken` → `child.kill()`）。

## 3. 外部进程的正确用法

### 3.1 收窄到唯一出口

全项目**只允许一个地方**调用 `spawn`：`src/core/proc/runner.ts`。

```
业务代码 → ProcessRunner.run(cmd, args, opts) → spawn
           ↑ 唯一出口：统一处理 编码 / 引号 / 超时 / 取消 / 日志
```

好处：跨平台差异、编码、超时、取消逻辑只写一次；测试时只需 mock 这一个接口。

### 3.2 跨平台差异（必须显式处理）

| 平台 | 现象 | 处理 |
|---|---|---|
| Windows | 有些工具只有 `.bat` / `.cmd`，`spawn` 直接调会 `ENOENT` | 走 `cmd.exe /c`，或 `shell: true` + **正确转义** |
| Windows | 路径含空格、中文、`(` `)` | 参数用数组传，不走字符串拼接 |
| Linux / macOS | 工具无扩展名，缺可执行位 | 探测时检查 `X_OK`，失败时给出明确提示 |
| 全平台 | 工具在 PATH 但插件找不到（GUI 启动的 PATH ≠ 终端 PATH） | 允许用户配置绝对路径，且探测失败时提示"请手动指定路径" |

### 3.3 输出处理的三个坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 不消费 stdout/stderr | 管道缓冲区写满 → 子进程阻塞 → **永久挂起且无输出** | 始终同时监听两个流，或调用 `child.stdout.resume()` |
| 混用 `close` 与 `exit` | 拿到的事件早于输出读完 → 诊断缺尾 | 用 `close` 事件判断结束 |
| 按 UTF-8 硬解 | Windows 下部分工具输出 GBK，出现乱码或替换字符 | 可配置编码；解析前先检测替换字符 U+FFFD 并告警 |

> **退出码不是唯一判据**：xvlog 在有 error 时退出码可能仍为 0（取决于参数）。
> 必须同时看输出内容，不能只看 `code`。

### 3.4 超时与取消

每个外部进程都必须带：
- **超时**（默认值写进参数表，用户可配）
- **可取消**（用户切文件 / 关闭文档时取消上一次调用）
- **并发上限**（同时最多 N 个，避免拖垮机器）

## 4. 降级策略：工具链不存在时怎么办

这是插件类项目**最重要的一张表**。缺失依赖时，"静默失败"是最坏选项，"崩溃"是次坏选项，正确答案是**明确降级并告知**。

| 能力 | 工具链可用 | 工具链缺失时的行为 | 状态栏 |
|---|---|---|---|
| 语法高亮 | TextMate（内置） | 始终可用 | 无提示 |
| 代码片段 | 内置 | 始终可用 | 无提示 |
| 语法检查（xvlog） | ✅ | **整簇关闭语法检查**，清除已有诊断 | ⚠ 语法检查不可用 |
| 格式化（外部 formatter） | ✅ | 命令执行时提示"未配置 formatter"，给配置入口 | 无 |
| 一键例化 | 内置解析 | 始终可用（不依赖外部工具） | 无 |

硬要求：

1. **整簇关闭，不留残迹**：切换到不可用状态时，必须 `diagnosticCollection.clear()`。否则用户会看到上一个工具链的旧红线一直挂着。
2. **说清原因**：提示文案包含"缺什么、去哪里配、当前探测到的路径"。
3. **不重复打扰**：同一原因只在状态栏提示一次，不反复弹窗。
4. **可自证**：`VeriKit: 显示诊断信息` 命令能一键打印探测结果与降级原因。

---

## 5. 启动与关闭的顺序

插件激活时按固定顺序执行，**任一步失败后进入降级而不是抛出**：

1. 读用户配置（工具链路径、编码、超时）
2. 探测工具链（存在性 → 版本 → 可用性；只做轻量调用，不做全量语法检查）
3. 注册命令、状态栏、诊断集合
4. 注册文档监听（打开/修改/关闭）
5. 打印一行启动日志：`verikit v0.1.3 build 42 | xvlog 2022.2 OK | formatter 未配置`

关闭时（`deactivate`）：
- 取消所有进行中的外部进程
- 清理临时文件
- 清空诊断集合

## 6. 用户数据的保护

| 数据 | 保护方式 |
|---|---|
| 用户源码 | 写盘前必须 diff 预览；支持撤销（走 `WorkspaceEdit`，而不是 `fs.writeFile`） |
| 用户配置 | 合并写入，只碰自己的键；改动前弹窗确认 |
| 缓存（索引、诊断历史） | 存 `context.storageUri` 或 `globalStorageUri`，不污染工作区 |
| 日志 | 默认不记录用户源码内容，只记路径与统计；用户可开"详细日志" |

> 用 `WorkspaceEdit` 而不是直接写文件，是为了让改动**可被 Ctrl+Z 撤销**。
> 这是插件与用户之间的基本契约。

## 7. 常驻进程：默认不启用，启用则须满足五条规则

> 早期版本把"0 常驻进程"当硬约束。实践下来更准确的目标不是"没有进程"，而是**"用户感知不到代价"**。
> 因此改为：**默认不带常驻进程；确有必要时可以引入，但必须满足下列规则与指标。**

### 7.1 先分清两种常驻，性价比差一个数量级

| | A. 工具链代理常驻 | B. 索引服务常驻 |
|---|---|---|
| 做什么 | 用常驻进程包住外部 CLI 调用 | 把符号索引放内存，增量更新 |
| 省掉什么 | 每次 spawn 的固定开销 | 全量重建索引 |
| 收益 | **小**（xvlog 自身耗时远大于 spawn 开销） | **大**（大工程从全量重扫变成只扫改动文件） |
| 结论 | ❌ 不做 | ⭕ 满足判据才做 |

### 7.2 启用判据（必须用实测数据，不能凭感觉）

```
判据：1000 个源文件的全量索引重建耗时 T
  T < 300 ms      → 不需要常驻，每次重建即可
  300 ms ~ 1 s    → 用磁盘缓存 + 增量，仍不必常驻
  T > 1 s         → 才讨论引入常驻
```

### 7.3 五条硬规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | **懒加载**：不在 `activate()` 里启动，首次需要时才起 | 否则用户开个空窗口也要背几十 MB |
| 2 | **崩溃即降级**：自动重连一次，仍失败则切回无常驻模式，**不弹窗** | 用户不该为架构选择买单 |
| 3 | **跟窗口生命周期绑定**：窗口关就退 | 否则多开几次窗口就一堆僵尸进程 |
| 4 | **必须有空闲退出**（如 10 分钟无请求） | 用户一天只写半小时代码，不该常驻一天 |
| 5 | **业务日志绝不能走 stdout** | stdio 是协议流，混一行日志就协议错乱，现象是"偶发卡死"，极难查 |

第 5 条的补白：调试时常忍不住 `console.log`，一打就把整个 JSON-RPC 流搞崩。
**日志一律走 `stderr` 或独立文件。**

### 7.4 "无感"必须可验收

| 指标 | 目标 | 测法 |
|---|---|---|
| 常驻进程内存 | < 60 MB | 任务管理器看进程树 |
| 启动时机 | 懒加载，激活日志中无启动记录 | 看 OutputChannel 首屏 |
| 空闲 CPU | 0%（不许轮询） | 静置 5 分钟后观察 |
| 退出 | 窗口关闭 / 工作区切换后 5 s 内退出，无残留 | 关窗口后看任务管理器 |

## 8. 现场调试的实用约定

| 约定 | 原因 |
|---|---|
| 调试前记录插件版本、VSCode 版本、工具链版本 | 出问题可回到已知状态 |
| 每次只改一个变量再重载 | 否则无法归因 |
| 重载后先执行"最小动作"（`VeriKit: 显示诊断信息`） | 确认插件真的活着 |
| 在**干净的测试工作区**里调试，不在真实工程里 | 避免污染用户文件 |
| OutputChannel 日志要保存下来 | 现象会消失，日志不会 |
| 怀疑是插件问题时，先用命令行跑同一个工具 | 快速区分"工具链问题"与"插件问题" |

## 9. 依赖变更的文档要求

任何一项发生变更（换工具链、加新 formatter、升级 VSCode 引擎版本、新增下载行为），必须更新：

1. `31_参数表.md`（自动生成）—— 新增配置项
2. `90_已知问题与限制.md` —— 旧问题是否还适用
3. `00_开发日志` —— 何时、改了什么、为什么
4. `01_项目进度` —— **重跑受影响阶段的验收，不要假设旧结论仍成立**
