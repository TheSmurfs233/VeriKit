# 04 测试先行

> **规则：任何逻辑改动，先在自动化测试里跑通，再进"手动可见"的实现。**
>
> 插件开发的一次手动验证：改代码 5 s + 编译 5 s + 重载窗口 10 s + 手点复现 30 s ≈ **50 秒起**，且不可重复（依赖你记得点哪几下）。
> 一次单元测试：**0.2 秒**。差 250 倍，且测试能覆盖边界、能重复、能防回归。

---

## 1. 四级测试金字塔

按"离真实 VSCode 的远近"分四级，成本递增、保真度递增、**数量应递减**。

| 级别 | 环境 | 能验证什么 | 不能验证什么 | 单次成本 |
|---|---|---|---|---|
| **L1 单元** | vitest，纯 Node | 解析、路径、字符串处理、状态机、归一化 | 任何 vscode API 行为 | 毫秒 |
| **L2 快照/基准** | vitest + golden 文件 | grammar 分词、诊断解析、例化输出 | 用户实际观感 | 秒 |
| **L3 集成** | `@vscode/test-electron` | 命令是否注册、诊断是否真的显示、激活时机 | 布局、动画、主题配色 | 十秒 |
| **L4 手动验收** | 真 VSCode，F5 | **观感**（颜色顺眼、悬停位置、弹窗时机） | 一切可量化指标 | 分钟 |

**原则**：能 L1 解决的不要用 L3，能被 L3 覆盖的不要靠 L4 手点。**L4 的结果永远不能作为判据**，只能作为"体验反馈"。

> 四级不是四选一。一个功能通常需要 L1（逻辑）+ L2（基准）+ L3（接线）+ L4（观感）各一条。

---

## 2. L1：单元测试（vitest）

### 2.1 唯一的硬前提

```
src/core/**     不能 import vscode
src/vscode/**   才可以 import vscode
```

这条约束决定了"能不能测"。一旦 `core` 里出现 `import * as vscode`，这个模块就永久失去自动化测试能力，只能靠 F5 手点。

### 2.2 适合 L1 的东西

| 目标 | 典型用例 |
|---|---|
| 诊断解析器 | 输入 xvlog 的原始 stderr 文本，输出结构化诊断数组 |
| 路径处理 | 含空格 / 中文 / UNC 路径 / 相对转绝对 |
| 模块解析 | `module foo #(parameter W=8) (input [W-1:0] d, output q);` → 端口表 |
| 工具链探测逻辑 | 给定伪文件系统结构，判断工具是否存在 |
| 命令行拼装 | 给定配置，生成 formatter / xvlog 的参数数组 |

### 2.3 写法要求

```ts
// test/unit/diag.normalize.test.ts
import { describe, it, expect } from 'vitest';
import { normalizeXvlog } from '../../src/core/diag/normalize';

describe('xvlog 诊断归一化', () => {
  it('解析单条错误', () => {
    const out = normalizeXvlog('ERROR: [VRFC 10-91] foo is not declared [/p/a.v:12]');
    expect(out).toHaveLength(1);
    expect(out[0].line).toBe(12);
    expect(out[0].severity).toBe('error');
  });

  it('空输出返回空数组', () => {
    expect(normalizeXvlog('')).toEqual([]);
  });
});
```

要点：
1. **一条用例只断言一个事实**，失败时能直接看出是哪个假设破了
2. **必须覆盖边界**：空输入、超长行、缺行号、多行诊断、非 UTF-8 字符
3. **用真实工具链的输出做样本**（从 OutputChannel 原样复制），不要自己编

## 3. L2：快照与基准（golden files）

这是本流程里**性价比最高的一级**：它把"我觉得对了"变成"和基准文件逐字节一致"。

### 3.1 目录约定

```
test/golden/
├── corpus/                 输入样本（.v 文件）
│   ├── basic_wire.v
│   ├── param_port.v        含 parameter 与位宽表达式
│   ├── broken_syntax.v     故意写错，用于诊断基准
│   └── cn_path_测试.v      中文文件名
├── expected/               期望输出（.json，与 corpus 一一对应）
│   ├── basic_wire.diag.json
│   └── ...
└── run.ts                  跑全量 corpus，逐项比对
```

**硬规则：`corpus/` 与 `expected/` 必须一一对应。** `doc_check.py` 检查这一点 —— 新增样本却不给期望值，比没有样本更糟（会让人误以为"通过"）。

### 3.2 两类基准

| 类型 | 基准内容 | 用途 |
|---|---|---|
| **诊断基准** | `[{line, col, severity, code, message}]` | 防"解析器悄悄丢诊断" |
| **分词基准** | `[{line, text, scope}]` | 防"改一处高亮，坏掉三处" |

生成方式：人工确认一次，`--update` 写盘，之后只读比对。**基准文件的每次变动都必须能在提交信息里解释。**

### 3.3 更新基准的纪律

```
基准变动 = 行为变动，必须在提交信息里写清楚：
  哪个样本、哪一项、从什么变成什么、为什么
```

禁止"报告红了就 `--update`"。那等于把基准变成"当前实现的复印件"，从此失去防回归能力。

## 4. L3：集成测试（@vscode/test-electron）

只验一类事：**接线对不对**。不验算法。

### 4.1 能覆盖的典型用例

```ts
// 命令注册
const cmds = await vscode.commands.getCommands(true);
expect(cmds).toContain('verikit.showDiagnostics');

// 诊断真的进了集合
const diags = vscode.languages.getDiagnostics(uri);
expect(diags[0].message).toContain('not declared');

// 语言识别（activationEvents 与 grammar 是否生效）
const doc = await vscode.workspace.openTextDocument(uri);
expect(doc.languageId).toBe('verilog');
```

### 4.2 别在这里做的事

- 不要断言 UI 细节（按钮位置、颜色）
- 不要依赖真实工具链（用 fixture 输出替代；真工具链放 L4）
- 不要串行依赖（每条用例自己准备状态，不依赖上一条）

## 5. L4：手动验收

只记录"观感类"结论，并且**必须带环境信息**：

```markdown
| 项 | 结论 | 环境 |
|---|---|---|
| 浅色主题下关键字对比度足够 | ✅ / ❌ | VSCode 1.9x / Default Light |
| 例化预览的 diff 视图可读 | ✅ / ❌ | 同上 |
| 悬停提示遮挡不超过 3 行代码 | ✅ / ❌ | 同上 |
```

> L4 的问题一旦能写成一个断言，就应当**立刻下移到 L3 或 L1**。
> L4 长期存在，说明观测手段没建好。

## 6. 环境漂移：测试脚本的首要敌人

插件项目的环境漂移比嵌入式更隐蔽，因为依赖链条更长：

| 漂移源 | 表现 | 固定方式 |
|---|---|---|
| Node 版本 | vitest / tsc 行为差异 | `.nvmrc` + `package.json engines` |
| VSCode 版本 | `engines.vscode` 不匹配 → 集成测试起不来 | 本地与发布都锁定同一版本 |
| 工具链版本 | xvlog 输出格式在不同版本间有差异 | 诊断基准里记录产生它的版本 |
| shell 与 PATH | 终端能跑，插件里 ENOENT | 探测时打印实际 PATH 与解析到的绝对路径 |

**加固措施**：测试脚本开头自证环境，让"跑错环境"立刻暴露。

```bash
echo "node : $(node -v)"
echo "tsc  : $(npx tsc -v)"
echo "xvlog: $(command -v xvlog || echo not-found)"
```

> 真实教训（从嵌入式项目移植过来的）：报错信息与"预期错误"不符时，
> **先确认你跑的是哪个工具链**，再查代码。曾经因为用错了 bash，
> 真正的错误被 `undefined reference to 'cosf'` 完全掩盖。

## 7. 不适用的场景（直接手动验，但要写明理由）

| 场景 | 为什么不自动化 | 补偿措施 |
|---|---|---|
| 配色 / 图标 / 主题适配 | 依赖渲染，无法断言"好看" | 截图留存，人工对比 |
| 弹窗 / 提示的时机与位置 | 依赖 UI 框架内部行为 | 固定一套手动检查清单 |
| 拖拽 / 输入法 / 快捷键冲突 | 依赖真实输入事件 | 每次发布前手点一遍 |
| 多平台差异（Windows/macOS/Linux） | 单机无法覆盖 | 至少保证探测与路径逻辑用 mock 覆盖三平台分支 |
| VSCode 版本升级带来的 API 变化 | 无法预知 | 收紧 `engines.vscode`，升级时跑全量 L3 |

**要求**：在阶段方案里写明"此项不做自动化，依据：…"，并**提高该项的手动验证强度**（写进验收清单，逐条打钩）。

## 8. "测试先行"的执行检查表

改动前自问：

- [ ] 这个改动有逻辑成分吗？（有 → 必须 L1 或 L2）
- [ ] 变化量能被一条断言捕获吗？（能 → 先写这条断言，看它失败，再实现）
- [ ] 有没有边界（空输入、超长、缺字段、非 UTF-8、路径含空格）需要覆盖？
- [ ] 受影响的 golden 基准有哪些？会不会连带改坏？
- [ ] 这个改动涉及 vscode API 吗？（涉及 → 需要 L3 覆盖接线）

改动后：

- [ ] 全量测试通过，基准确认无意外变动
- [ ] 新增的断言保留在 `test/` 里（作为回归）
- [ ] 若发现新坑，写进对应框架文档的"坑"章节

---

## 9. 一句话总结

> **插件项目最容易死的不是逻辑，是"接错了线还看着正常"。**
> L1 守逻辑，L2 守基准，L3 守接线，L4 只守感觉。
> 把 L4 当判据的项目，一定会在某次"看着没问题"的提交里埋下雷。
