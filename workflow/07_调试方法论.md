# 07 调试方法论

> 本章是整个流程中最"贵"的部分 —— 它来自真实 bug 的代价。
>
> 核心命题：**判断"系统是否正常"的判据本身，是最容易写错的东西。**
> 而在插件项目里它更隐蔽，因为**编辑器"看起来正常"的容错度极高**：
> 少着色一个关键字、少报一半诊断，界面依然"看着挺好"。

---

## 1. 第一原则：判据必须是"不变量"

### 1.1 什么是不变量

在**工况变化时保持不变**的量，才适合作为判据。对插件来说，"工况"就是主题、字体、窗口大小、文件顺序、机器配置。

| 场景 | ❌ 会漂移的量 | ✅ 不变量 |
|---|---|---|
| 高亮是否正确 | 肉眼观感（受主题、缩放、字体影响） | 固定 corpus 的 **scope 序列**（`keyword.control.verilog` / `comment.line.verilog` …） |
| 诊断是否解析完整 | 编辑器里"有没有红线" | **诊断条数 + (行, 列) 集合**，与 CLI 原始输出严格相等 |
| 例化输出是否正确 | "生成的代码能编译" | 与手写基准**逐字节相等**（含端口顺序、位宽表达式、注释） |
| 性能是否退化 | "感觉有点卡" | 单次诊断耗时（ms，实测，固定样本、固定机器） |

### 1.2 案例：注释里的关键字被着色

**现象**：改了 grammar 里一条 `match` 规则后，整体高亮"看着没问题"，但某次滚动代码时发现
`// module foo is disabled` 这行注释里的 `module` 是关键字颜色。

**数据**（corpus 全量快照 diff）：

| 统计项 | 改动前 | 改动后 |
|---|---|---|
| 总 token 数 | 1842 | 1842 |
| scope 为 `keyword.control.verilog` 的 token | 96 | **99** |
| 差异位置 | — | 3 处，全部位于注释行内 |

**分析**：新增规则 `"match": "\\bmodule\\b"` 排在 `comment` 规则**之前**。TextMate 的规则是
**先匹配先赢**，注释规则还没轮到，关键字规则已经吃掉了注释里的文本。

**结论**：调整规则顺序不是"随便放"，而是**语义**：越具体的（comment / string）越要排在
越宽泛的（keyword）之前。

**如果没有快照**：这个 bug 会活到用户某天截图问你"为什么注释里的字是蓝的"为止 —— 而且之后
每次改 grammar 都会重现一次。

### 1.3 如何检验判据是否是不变量

问自己："如果**其他**部分都不理想（主题换了、机器慢了、文件顺序变了），这个量会变吗？"

- 颜色会变 → 不是不变量
- scope 序列不会变 → 是不变量

## 2. 第二原则：不要用被验证的对象验证它自己

### 2.1 案例：诊断"少报一半"

**现象**：语法检查"能用了"，编辑器里出现了红线。

**数据**：同一个 `broken_syntax.v`，两个来源对比：

| 来源 | 诊断条数 |
|---|---|
| 命令行直接跑 `xvlog broken_syntax.v` | **23** |
| 插件诊断面板显示 | **11** |

**根因**：xvlog 的部分诊断是**多行**的（首行给位置，后续行给上下文提示）。解析器用的是
`/(ERROR|WARNING):\s*(.*)/g`，只抓到了首行，把后续行当噪声丢掉了。**丢掉的全是 warning。**

**为什么肉眼发现不了**：编辑器里有 11 条红线，"语法检查在工作"这个判断成立。用户会在
第 12 个真实错误上浪费半小时。

**正确做法**：诊断的判据不是"有没有红线"，而是**与 CLI 原始输出的诊断集合严格相等**。
这就需要一个**独立基准**：一个不经过插件的小脚本，直接读 CLI 输出并计数。

```
判据 = (插件输出的诊断集合) === (独立脚本解析 CLI 得到的集合)
```

### 2.2 通用形式

| 反模式 | 正确做法 |
|---|---|
| 用解析器的输出判断解析是否完整 | 用**原始文本**做基准（原始行数 / 关键字计数） |
| 用插件的日志判断插件是否运行 | 用**外部观察**（进程列表、临时文件时间戳） |
| 用索引自己判断索引是否收敛 | 用**文件系统真实内容**（`grep module` 的条数） |
| 用 UI 上的红点数判断问题数 | 用**结构化导出**（`FPGA: 导出诊断 JSON`） |

### 2.3 没有独立基准时怎么办

如果确实没有第二个来源，则：
- 改用**物理/逻辑约束**（如"诊断的行号必须在 1..总行数 之内"、"端口数必须等于端口表长度"）
- 并明确记录"此处缺少交叉校验，误判无法被第二来源发现"

## 3. 第三原则：状态切换必须有硬优先级

### 3.1 案例：切换工具链后旧诊断残留

**系统结构**：

```
诊断提供者 A（xvlog）  ─┐
                        ├→ 同一个 DiagnosticCollection
诊断提供者 B（iverilog）─┘
```

用户在设置里把工具链从 xvlog 改成 iverilog 后，**xvlog 的红线依然挂在编辑器里**，
而且新诊断和旧诊断混在一起，行号对不上。

**根因**：两个提供者都直接往同一个 collection 写，谁后跑谁赢；切换时没人负责清理。

**正确做法**：

```ts
// ① 只有一个 owner，任何人不得直接持有 collection
class DiagnosticManager {
  set(source: string, diags: Diagnostic[]) {
    this.collection.clear();        // 整簇替换，不合并
    this.collection.set(this.uri, diags);
    this.owner = source;
  }
  clearAll() { this.collection.clear(); this.owner = null; }
}

// ② 调度处加硬优先级：只有当前选中的工具链有执行权
if (toolchain.active === 'xvlog') { runXvlog(); }
else if (toolchain.active === 'iverilog') { runIverilog(); }
else { diagManager.clearAll(); }   // 一个都没有 → 明确清空
```

**原则**：
- 状态切换不能只靠"标志位"，必须有**结构性保证**（只有一个写入口）
- 任何 `setXxx()` 都不应该带"启动"副作用
- 后执行的一方必须显式检查"我是否有权执行"

### 3.2 同一原则的另一处应用：竞态

文档修改触发诊断，用户快速打字会连发多个请求。**慢的旧请求如果后返回，会覆盖新结果** ——
表现为"显示的诊断对不上当前代码"。

```ts
// ❌ 没有序号，谁后返回谁写
async function onEdit(doc) { const d = await lint(doc); manager.set(d); }

// ✅ 带请求序号，过期结果直接丢弃
let seq = 0;
async function onEdit(doc) {
  const my = ++seq;
  const d = await lint(doc);
  if (my !== seq) return;          // 我已经过期了，不写
  manager.set(d);
}
```

## 4. 第四原则：先测量，再修改

### 4.1 反模式

```
现象：语法检查不工作，编辑器里没有红线
猜测 1：激活事件没配对      → 改 package.json → 无效
猜测 2：languageId 不是 verilog → 改 selector → 无效
猜测 3：正则写错了          → 反复改正则 → 无效
（两天过去）
```

### 4.2 正确流程

```
步骤 1：加仪表 —— 把内部量打出来
        （当前文档的 languageId、选中的工具链、探测到的可执行文件绝对路径、
          命令行参数、退出码、stdout/stderr 原始字节数、解析出的诊断条数）
步骤 2：在**失败的那一刻**抓数据
步骤 3：让数据排除假设
步骤 4：只改被数据支持的那一处
```

### 4.3 案例：一次"仪表定生死"

**现象**：语法检查"没有反应"。

加一个 `FPGA: 导出诊断 JSON` 命令后一次抓取：

```
=== fpga-plugin v0.1.3 build 42 ===
doc      : /w/a.v   languageId=plaintext   lines=248
toolchain: xvlog  (configured) -> C:\Xilinx\Vivado\2022.2\bin\xvlog.bat  [exists]
cmd      : cmd.exe /c "C:\Xilinx\...\xvlog.bat" --incr --log xvlog.log a.v
exit     : 0      stdout=0 B   stderr=0 B     elapsed=12 ms
parsed   : 0 diagnostics
```

**一条信息就定位了**：

- `languageId=plaintext` ← 语言根本没被识别成 verilog，**与诊断逻辑完全无关**
- `exit=0, 0 字节输出, 12 ms` ← 进程其实立刻就返回了，说明命令没真跑起来
- `[exists]` ← 文件存在，不是路径问题

→ 结论：**grammar / language 关联没生效**，诊断链路压根没被触发。

如果没打这几个量，只能在"正则、selector、激活事件"之间反复猜。

### 4.4 仪表设计要点

| 要点 | 说明 |
|---|---|
| 打印**内部状态**，不只打印输出 | `languageId`、当前工具链、解析条数，比"命令失败"有信息量得多 |
| 打印**比例与一致性** | `显示 11 条 / CLI 23 条` 比 `显示 11 条` 更能说明问题 |
| 打印**多个相关量放在一起** | 便于交叉判断（工具链 + 命令 + 退出码 + 字节数） |
| 打印**绝对路径**，不打印配置值 | 配置写的是 `xvlog`，实际解析到哪才是真相 |
| 输出格式**可被脚本解析** | 便于回归与自动比对 |

## 5. 第五原则：一次只改一个变量

### 5.1 为什么

一次改三条 grammar 规则，结果"看起来更好了"——你无法知道是哪条起了作用，也无法知道
另外两条是不是引入了新问题。

### 5.2 对照实验的设计

```
基线：不改任何东西，跑全量 corpus，记录 token 数、诊断数
实验 A：只改规则 1，跑全量 corpus，与基线 diff
实验 B：只改规则 2，跑全量 corpus，与基线 diff
对比：三个结果放在一起看
```

**关键：必须跑全量，不能只跑你正在测的那个文件。** grammar 的规则是互相影响的，
改 A 文件的行为，往往在 B 文件上出问题。

### 5.3 案例：区分"解析问题"与"路径问题"

现象：`中文路径/测试.v` 诊断不生效，别的文件都正常。

| 实验 | 操作 | 结果 |
|---|---|---|
| 1 | 把同一文件复制到纯英文路径 | **正常** |
| 2 | 把中文目录名改成英文，文件内容不变 | **正常** |
| 3 | 在命令行用引号包裹中文路径直接跑 xvlog | **正常** |

→ 结论：**与解析无关，与"参数传递时没加引号"有关**。
如果只做实验 1 就收工，会误判为"编码问题"，然后去改编码检测 —— 完全修错方向。

## 6. 症状 → 根因 对照表

建立并维护这样一张表，是最高效的知识沉淀方式。**这张表必须随项目生长。**

| 症状 | 首先怀疑 | 验证方法 |
|---|---|---|
| 编辑器里完全没有红线 | 语言没识别 / selector 不匹配 | 打印 `languageId` 与 `documentSelector` |
| 有红线但行号整体偏 1 | 0-based 与 1-based 混用 | 拿一条已知位置的错误对照 |
| 只显示第一条诊断 | 正则缺 `g` 标志 / 只 `exec` 了一次 | 打印解析条数 vs 原始行数 |
| 诊断不随编辑更新 | 没监听 `onDidChangeTextDocument` | 打日志看回调是否触发 |
| 快速打字后诊断错位 | 竞态：旧结果覆盖新结果 | 加请求序号，打印 seq |
| 诊断切换工具链后不消失 | 没 `clear()`，两个提供者写同一集合 | 搜所有写集合的地方 |
| 终端能跑，插件里 ENOENT | `.bat` 未走 `cmd /c` / 插件 PATH ≠ 终端 PATH | 打印实际解析到的绝对路径 |
| 进程无输出且永久挂起 | stdout 管道写满未被消费 | 加超时，同时监听两个流 |
| 输出乱码 / 出现 U+FFFD | 编码不是 UTF-8 | 打印原始字节数与前 64 字节 |
| 路径含空格就失败 | 命令用字符串拼接而非参数数组 | 打印最终 argv |
| 首次打开正常，之后不工作 | 监听只在激活时注册了一次 / 被 dispose 了 | 打印监听注册/销毁次数 |
| 编辑器整体卡顿 | 同步 I/O 或 `execSync` 阻塞宿主 | 搜 `execSync`、`readFileSync` |
| 例化输出"能编译但端口顺序不对" | 基准用"能编译"当判据 | 改为逐字节对比基准 |

## 7. 假设被推翻时，必须显式记录

### 7.1 为什么

被推翻的假设是**最值钱的知识**：它防止你再走一次。

### 7.2 记录格式

```markdown
### 已推翻的假设
| # | 假设 | 推翻依据 | 真正原因 |
|---|---|---|---|
| 1 | 语法检查失效是正则写错 | 解析条数=0，正则根本没被调用 | languageId=plaintext，链路未触发 |
| 2 | 诊断少报是 xvlog 本身不报 warning | CLI 独立跑出 23 条 | 多行诊断只取了首行 |
| 3 | 中文路径是编码问题 | 命令行直接跑正常 | 参数未加引号 |
```

## 8. 调试的收尾

问题解决后必须完成三件事，否则这次调试的价值会流失：

1. **写进开发日志**：现象、数据、推理、修法、验证
2. **写进框架文档的"坑"章节**：后来者能直接看到
3. **把判据变成自动化断言**：防止回归

```ts
// 例：把"多行诊断必须全部保留"固化成断言
it('xvlog 多行诊断不丢失', () => {
  const raw = readFixture('xvlog_multiline.txt');   // 真实输出，23 条
  expect(normalizeXvlog(raw)).toHaveLength(23);
});

// 例：把"注释内容不得被识别为关键字"固化成快照
it('注释内的 module 不是关键字', () => {
  expect(scopesOf('// module foo')).toEqual(['comment.line.verilog']);
});
```

## 9. 一句话总结

> **判据设计错误的代价，远大于算法错误的代价。**
> 逻辑错了会立刻报错，判据错了会让界面"看着挺好"——
> 而"看着挺好"最难查，也最容易让用户在某个真实错误上白费半小时。
