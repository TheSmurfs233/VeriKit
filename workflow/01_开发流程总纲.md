# 01 开发流程总纲

> 本文定义项目的**五个阶段**与**五个门禁**。
> 阶段是"能力的成长"，门禁是"过关的条件"。二者不可混用。

---

## 1. 五个阶段

| 阶段 | 名称 | 产出 | 典型时长 |
|---|---|---|---|
| **A** | 立项与需求 | 需求清单、约束、验收总目标 | 1~3 天 |
| **B** | 方案与架构 | 方案文档、架构文档骨架、阶段计划 | 3~7 天 |
| **C** | 分阶段实施 | 每阶段：方案 → 测试 → 实现 → 验证 → 提交 | 主要工期 |
| **D** | 集成与矩阵验证 | 全链路联合测试、边界与异常测试、跨平台验证 | 1~2 周 |
| **E** | 交付与文档冻结 | 使用说明、已知问题、参数表定稿 | 2~3 天 |

---

## 2. 五个门禁

每一个门禁都是**"没有证据就不放行"**。

### G1 需求门禁（A → B）

- [ ] 需求写成条目，每条**可验证**（有数值阈值或可观测现象）
- [ ] 约束写清楚（运行环境、依赖、性能上限、体积上限）
- [ ] 明确"这一版不做什么"（防止范围膨胀）

### G2 方案门禁（B → C）

- [ ] 总体方案有**备选路线**，并写明为什么选当前这条
- [ ] 阶段划分完成（见 `03_阶段推进与验收`）
- [ ] 每阶段的验收标准已量化，且**指明用哪一级测试**（L1~L4）
- [ ] 风险清单与对策
- [ ] 评审记录归档（谁、何时、结论）

### G3 阶段门禁（C 内，每个阶段）

一个阶段只有同时满足下列条件才算完成：

- [ ] 验收标准**逐条**实测通过（数据进开发日志）
- [ ] 静态检查 0 错误 0 警告（`tsc --noEmit` + `eslint --max-warnings=0`）
- [ ] 全部自动化测试通过，基准文件无意外变动
- [ ] 文档检查通过
- [ ] 相关架构文档已更新
- [ ] 已提交并推送

> **禁止跳阶段**。发现前一阶段有缺陷时，回到那个阶段补，
> 不要在新阶段里"顺手绕过去"——那会变成技术债。

### G4 集成门禁（D → E）

- [ ] 全链路（激活 → 探测 → 编辑 → 诊断 → 关闭/重载）反复通过
- [ ] 异常场景逐项验证（依赖缺失、文件不存在、权限不足、**超大文件**、编码异常）
- [ ] 降级行为全部实测触发过，且**用户能看懂提示**
- [ ] 长时运行（≥ 30 min 连续编辑）无内存增长、无监听泄漏、无诊断堆积
- [ ] 跨平台分支逻辑（三大 OS）被 mock 覆盖

### G5 交付门禁（E 结束）

- [ ] 使用说明能让人在不问你的情况下跑起来
- [ ] 参数表与实际代码逐项核对一致（**自动生成，不手写**）
- [ ] 已知问题清单完整（含"不打算修"的）
- [ ] 版本号、打包产物、文档基线一致（可用脚本校验）

## 3. 阶段内的标准动作（最重要）

每个阶段内部按固定五步执行，**顺序不可颠倒**：

```
① 方案   写成文档 → 评审
② 测试   先写能失败的测试（见 04_测试先行）
③ 实现   写代码，版本号 +1
④ 验证   三方验证（见 05_验证与提交规范）
⑤ 提交   一个阶段一个提交，信息含证据
```

### 为什么"测试"必须排在"实现"前面

- **成本差 250 倍**：一次手动验证 ≈ 50 s（编译 + 重载窗口 + 手点），一次单元测试 ≈ 0.2 s
- **测试是可重复的**：手动验证受"你记得点哪几下"影响，同样的代码可能得到不同结论
- **测试能覆盖边界**：空输入、超长行、缺字段、路径含空格 —— 手动几乎不可能刻意制造
- **先写测试会逼你想清接口**：写不出测试，通常说明这个函数职责不清

### 例外：哪些不需要自动化测试

| 类别 | 例子 | 处理方式 |
|---|---|---|
| 纯视觉 | 配色、图标、主题适配 | 写进手动检查清单，验收时逐条打钩 |
| 交互时序 | 弹窗时机、悬停位置、快捷键 | 同上 |
| 平台专有行为 | 特定 OS 的文件对话框 | 同上，并记录到 `90_已知问题` |

**要求：在方案里写明"此项不做自动化，依据：…"，不能默认"忘了写"。**

## 4. 架构与阶段的关系

```
         ┌─────────────────────────────┐
         │   表现层（vscode 适配层）      │  ← 命令、诊断集合、状态栏、视图
         ├─────────────────────────────┤
         │   能力层（core，零 vscode 依赖）│  ← 解析、归一化、索引、路径
         ├─────────────────────────────┤
         │   进程层（ProcessRunner）      │  ← 唯一 spawn 出口
         └─────────────────────────────┘
                      ↓
              外部工具链 / 本机环境
```

**分层的第一目的是可测试性**：能力层不依赖 vscode，才能在 vitest 里跑；
一旦某个模块混进了 `import * as vscode`，它就永久失去自动化测试能力。

## 5. 文档与阶段的关系

| 文档 | 何时写 | 何时更新 |
|---|---|---|
| `00_开发日志` | 每天/每次实验 | **追加式**，永不改旧条目 |
| `01_项目进度` | 立项 | 每阶段结束 |
| `10_框架_主架构` | 方案阶段 | 架构变化时 |
| `11+_框架_子系统` | 该子系统进入实施前 | 该子系统每次改动 |
| `18_待确认清单` | 随时 | 有了结论就迁出 |
| `30_命令手册` | **自动生成** | 每次 `contributes.commands` 变动 |
| `31_参数表` | **自动生成** | 每次 `contributes.configuration` 变动 |
| `90_已知问题` | 发现第一个已知限制 | 每次新增/关闭 |

> **判断标准**：如果"另一个你会问什么"，就把那个问题的答案写下来。
>
> **"自动生成"的意思**：命令清单与配置项在插件项目里本身就是代码
> （`package.json` 的 `contributes`），手写一份文档必然过期。让脚本从源头生成，过期问题从根上消失。

## 6. 阶段划分的原则

好的阶段划分满足：

1. **每个阶段产出一种可独立验证的能力**（不是"写了一堆代码"）
2. **后一阶段依赖前一阶段的输出**（否则可以并行或合并）
3. **每个阶段的失败是"局部"的**（不会让此前工作全部作废）
4. **每个阶段都能在 1~5 天内完成**（超过就再拆）

反例（错误划分）：
- ❌ "实现全部功能" —— 无法验证，无法定位失败
- ❌ "先写解析器，再想怎么测" —— 阶段没有验收标准
- ❌ 按代码目录拆（"先写 src/core，再写 src/vscode"）—— 每层单独都无法证明"对了"

正例（按"能力链"拆，来自插件项目的实际划分）：

```
S0 骨架与门禁          → 产出：F5 能起、verify.sh 四段全绿
S1 可观测与工具链探测   → 产出：能打印真实环境，缺失时有明确降级
S2 文本层（高亮/片段）  → 产出：token 快照与基准可回归
S3 索引层（模块/端口）  → 产出：模块树正确、例化输出等于基准
S4 诊断层（语法检查）   → 产出：诊断集合与 CLI 输出严格相等
S5 格式化层（外部调用） → 产出：格式化后语义等价、可一键撤销
```

**注意 S3 的打包**：模块树、一键例化、端口提示、跳转补全 **共用同一个跨文件索引**。
如果拆成四个阶段，会把同一个索引写四遍。

**注意 S2 的拆分**：先"能着色"，再"着得准"。
把"实现"和"验证"拆开，可以在实现有误时立刻发现，而不是等到功能失败时再回头猜。

## 7. 遇到的常见推进错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 边写边想需求 | 反复返工 | 先补 G1 |
| 跳过测试直接 F5 手点 | 出问题无法区分"逻辑错"还是"接线错" | 按阶段走，L1/L3 分工 |
| 一个提交里改五个东西 | 出问题无法归因 | 一次一改 |
| 用"看起来可以"代替数据 | 后续所有结论都不可信 | 用快照 / 导出 JSON 做判据 |
| 文档等"做完再补" | 补的时候已经忘了为什么 | 边做边记 |
| 依赖缺失就吞异常 | 用户以为一切正常，实际半残 | 明确降级 + 状态栏提示 |
| 加功能不加基准样本 | 下次改动静默破坏旧行为 | 功能与 corpus 同步增加 |

## 8. 新工程启动模板

```markdown
## 项目：<名称>

### A. 需求（可验证）
| # | 需求 | 验收标准（可量化） | 优先级 |
|---|---|---|---|

### B. 约束
- 运行环境：<OS / VSCode 版本 / Node 版本>
- 依赖：<外部程序、版本、是否必须>
- 性能：<首次激活耗时上限 / 单文件诊断耗时上限>
- 体积：<安装包大小上限>
- 平台：<Windows / macOS / Linux，各自差异>

### C. 阶段计划
| 阶段 | 目标（可验证的能力） | 验收标准 | 验证级别(L1~L4) | 依赖 |
|---|---|---|---|---|
| S0 | | | | |

### D. 不做的事
- <明确排除的内容>

### E. 风险
| 风险 | 影响 | 对策 |
|---|---|---|
```

填写上述模板 = 完成 A 阶段，可进入 B。
