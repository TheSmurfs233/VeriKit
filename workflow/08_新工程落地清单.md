# 08 新工程落地清单

> 从零搭建时，按此清单逐项打钩。全部完成 = 流程已落地。
>
> 顺序不是随意的：**先建立"改坏了能立刻知道"的能力，再写功能。**
> 反过来做（先堆功能），等你想补测试时会发现所有逻辑都和 `vscode` 耦合在一起，补不动。

---

## 阶段 0：工程骨架（半天）

- [ ] 目录结构建立

```
工程根/
├── src/
│   ├── extension.ts       激活入口（只做装配，不含业务逻辑）
│   ├── core/              ★ 禁止 import vscode
│   └── vscode/            适配层：命令、诊断、状态栏、视图
├── grammars/              *.tmLanguage.json + snippets
├── test/
│   ├── unit/              vitest
│   ├── golden/            corpus + expected
│   ├── integration/       @vscode/test-electron
│   └── doc_check.py
├── docs/
├── workflow/              本流程（复制）
└── verify.sh
```

- [ ] `package.json` 建立，最少包含：`engines.vscode`、`main`、`activationEvents`、`contributes.commands`（一个占位命令即可）
- [ ] `tsconfig.json` 开启 `strict`、`noUnusedLocals`、`noImplicitAny`
- [ ] `BUILD_ID` 常量建立（`src/core/version.ts`），激活时打印一行版本
- [ ] `docs/00_开发日志.md` 建立（写第一条"项目启动"）
- [ ] `docs/01_项目进度.md` 建立（填 A 阶段的需求/约束/阶段计划）
- [ ] `docs/10_框架_三层架构.md` 建立骨架（分层、数据流、进程边界）
- [ ] `docs/18_待确认清单.md` 建立（把没想清楚的问题先记下）
- [ ] `docs/90_已知问题与限制.md` 建立（先写"暂无"）
- [ ] 第一条提交：`chore: 工程骨架 + 文档体系`

## 阶段 1：可构建可验证（半天~1 天）

- [ ] `tsc --noEmit` 通过，**0 error 0 warning**
- [ ] `eslint . --max-warnings=0` 通过
- [ ] `vitest` 可运行，至少 1 条断言通过
- [ ] `test/golden/run.js` 可运行（哪怕只有一个样本）
- [ ] `test/doc_check.py` 可运行（先只查版本号一致性）
- [ ] 五段串成一个 `verify.sh`，输出 `ALL GREEN`

> 此时还没有任何功能，但**"改坏了能立刻知道"**的能力已经建立。
> 这一步省掉，后面每一步都在裸奔。

## 阶段 2：可观测（半天）

- [ ] `OutputChannel` 建成，激活第一行打印 `vX.Y.Z build N | node | 工具链状态`
- [ ] 状态栏项建成（显示工具链状态 / 诊断数）
- [ ] 命令 `FPGA: 显示诊断信息`（打印当前文档 languageId、配置、解析路径、版本）
- [ ] 命令 `FPGA: 导出诊断 JSON`（把内部解析结果写成结构化 JSON）
- [ ] `30_命令手册.md` 由 `package.json` 生成，`doc_check.py` 校验条数
- [ ] 提交：`feat: 可观测通道与诊断导出`

> **没有可观测性就没有验收**。这一步不能省。
> 后面每一次"为什么没反应"，都要靠这两个命令活着。

## 阶段 3：外部进程边界（1 天）

- [ ] `src/core/proc/runner.ts` 建立，**全项目唯一 `spawn` 点**
- [ ] 支持：参数数组传参（不拼字符串）、超时、取消、同时消费 stdout/stderr、`close` 事件判结束
- [ ] 工具链探测（`core/toolchain/detect.ts`）：配置值 → 绝对路径 → 存在性 → 版本
- [ ] 探测逻辑用 mock 文件系统覆盖三平台分支（`.bat` / 无扩展名 / 路径含空格与中文）
- [ ] 降级行为落地：缺失时**整簇关闭**相关功能 + 状态栏提示原因
- [ ] 提交：`feat: ProcessRunner 与工具链探测（含降级）`

> 这一层做不好，后面所有工具链功能都会踩同一个坑。
> 参考 `06_外部依赖与安全` §3。

## 阶段 4：第一个可见功能（按阶段计划推进）

- [ ] 写出阶段方案（`templates/t_阶段方案.md`），指明用哪一级测试
- [ ] **先建 corpus 与基准**（哪怕是手工确认的一版）
- [ ] 先写测试并让它失败（L1 / L2）
- [ ] 实现 + `BUILD_ID` +1
- [ ] 三方验证通过（`verify.sh` 绿）
- [ ] **手动验收**，数据进开发日志（记录 VSCode 版本、主题、工具链版本）
- [ ] 更新进度表与架构文档
- [ ] 提交：`feat: S<n> <能力>（实测 …）`

之后每个阶段重复阶段 4。

## 每个功能开发时的自检

```markdown
开工前
- [ ] 这个功能在 docs/01 里有对应阶段吗？
- [ ] 验收标准可量化吗？用哪一级测试证明？
- [ ] 逻辑放在 core 里吗？（放 vscode/ 里就测不了）
- [ ] 会写用户文件吗？（会 → 必须走预览模式）

实现中
- [ ] core 层有没有 import vscode？（有 → 拆分）
- [ ] 边界（空输入 / 超长 / 路径含空格中文 / 工具链缺失）处理了吗？
- [ ] 判据用的是不变量吗？（不是"看着对"）
- [ ] 状态切换有硬优先级吗？（只有一个写入口）
- [ ] 异步请求有竞态保护吗？（请求序号 / 取消）

提交前
- [ ] tsc 0E/0W
- [ ] eslint 0 warn
- [ ] 单元测试 + 基准全过，基准变动可解释
- [ ] 文档检查 PASS
- [ ] BUILD_ID +1
- [ ] 文档已同步
- [ ] 提交信息含根因与验证

手验后
- [ ] 数据记进开发日志（含环境）
- [ ] 验收标准逐条核对
- [ ] 进度表更新
- [ ] 发现的新坑写进架构文档
```

## 常见"落地失败"的征兆

| 征兆 | 说明 | 补救 |
|---|---|---|
| `01_项目进度` 一周没更新 | 进度已不可信 | 立刻补，冻结当前状态 |
| 提交信息都是 "update" | 历史失去价值 | 从下一次开始写根因 |
| 测试从来没跑过 | 回归保护缺失 | 先补 10 条最关键的断言 |
| `verify.sh` 长期是红的还照样提交 | 门禁形同虚设 | 修到绿，或删掉该项检查 |
| 加了功能但没加 corpus | 下次改动静默破坏旧行为 | 功能与样本同步增加 |
| 调试全靠临时 `console.log` | 观测性不足 | 固化成 `导出诊断 JSON` 命令 |
| 基准文件总在 `-u` | 基准失去防回归能力 | 每次变动必须在提交信息里解释 |
| 所有逻辑都写在 `extension.ts` 里 | 无法单测，无法复用 | 尽早拆到 `core/`，越晚越贵 |
| 每次都靠 F5 手点回归 | 效率低且漏测 | 把能断言的都下移到 L1~L3 |

## 最小投入的落地顺序

如果时间有限，按此顺序：

```
1. BUILD_ID + 激活日志            （10 分钟，收益最大）
2. docs/01 进度表                 （30 分钟，决定项目不迷路）
3. 一个"导出内部状态"的命令        （1 小时，决定能不能调试）
4. 版本号一致性检查脚本            （30 分钟，防文档过期）
5. corpus + 基准 + 快照脚本       （半天，防回归）
6. 其余文档                       （随阶段推进补齐）
```
