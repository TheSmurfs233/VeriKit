# 05 验证与提交规范

> **提交不是"我改完了"，而是"我证明它没坏"。**
> 每一次提交都必须携带证据，否则它只是把不确定性推给了未来的自己。

---

## 1. 三方验证门禁

任何提交前，三条必须全绿：

| # | 验证 | 命令（按工程替换） | 通过标准 |
|---|---|---|---|
| 1 | **静态检查** | `tsc --noEmit && eslint . --max-warnings=0` | **0 error, 0 warning** |
| 2 | **自动化测试** | `vitest run` + `node test/golden/run.js` | 全过，且基准无意外变动 |
| 3 | **文档检查** | `python test/doc_check.py` | `PASS` |

### 为什么警告也要清零

- 警告是"工具已经发现的可疑之处"，其中相当一部分是真 bug（未 await 的 Promise、隐式 any 掩盖了拼写错误）
- 一旦允许警告存在，新警告就会被淹没在旧警告里
- 清零成本很低（通常一到两次提交），收益是永久的

**具体做法**：`--max-warnings=0` 写进脚本，而不是靠自觉。

### 三方各自守什么

| 验证 | 守住的防线 |
|---|---|
| 静态检查 | 类型正确性、未使用变量、未处理 Promise、可能的 null |
| 自动化测试 | 逻辑正确性、基准回归（防止"修好 A 改坏 B"）、接线正确性 |
| 文档检查 | 文档与代码的一致性（版本号、命令数、配置数、样本与基准对应） |

**三者互补，缺一都会漏**：编译通过但解析器逻辑错、逻辑对但文档过期，都是常见失败模式。

## 2. 版本号规则

### 2.1 双版本号：语义化 + 单调 build

```jsonc
// package.json
{ "version": "0.4.1" }
```

```ts
// src/core/version.ts
export const BUILD_ID = 37;   // 每次"可加载进 VSCode 的改动" +1
```

| 字段 | 用途 | 规则 |
|---|---|---|
| `version`（semver） | 给人看、给市场/依赖看 | 新增能力 +0.1，修 bug +0.0.1 |
| `BUILD_ID`（整数） | 给校验与追溯用 | **只增不减**，任何可加载的改动都 +1 |

**为什么要两个**：semver 会反复（0.4.1 → 0.4.2 → 下次开发又回到 0.4.x），
而 `BUILD_ID` 单调递增，才能作为"这一次实验到底是哪个产物"的锚点。

### 2.2 什么算"可加载的改动"

- 改了 `src/**`、`package.json`、`grammars/**` → **+1**
- 只改文档、只加测试、只改注释 → 不 +1

### 2.3 版本号是"证据锚点"

```
开发日志：诊断 23/23 相等，v0.4.1 build 37
进度表：  S4 完成，证据 build 37
基准文件：由 xvlog 2022.2 产生，适用 build 37 之后
```

有了它，才能回答："这个结论是哪个产物测出来的？"

### 2.4 启动时打印

激活的第一行日志必须是版本：

```
[verikit] verikit v0.4.1 build 37 | node 24.21 | xvlog 2022.2 OK | formatter 未配置
```

**没有版本号的日志等于无法追溯的实验。** 调试时第一件事就是看这一行。

## 3. 提交信息规范

### 3.1 结构

```
<一句话标题（做了什么，≤ 50 字）>

<问题/背景：现象 + 触发条件>

<根因：为什么会出现>

<修法：怎么改的，关键决策及理由>

<验证：静态检查 / 测试 / 基准变动>
```

### 3.2 正面示例

```
诊断解析改为按位置行聚合，修复 warning 丢失 12 条（build 37）

现象(14:20): 同一个 broken_syntax.v，命令行 xvlog 报 23 条，
插件诊断面板只有 11 条；缺的 12 条全部是 warning

根因: 解析器用 /^(ERROR|WARNING):(.*)/ 逐行匹配,
  而 xvlog 的 warning 是两行——首行给位置, 次行给上下文说明。
  次行没有级别前缀, 被当成噪声丢弃, 导致所有 warning 静默丢失

修正: 改为"遇到带级别前缀的行才新建一条, 其余非空行并入上一条 message"
  同时把 bench 文件里 23 条真实输出固化为回归断言

验证: tsc 0E/0W; eslint 0 warn; vitest 42/42;
  golden 全量 6 个样本无意外变动; 诊断 23/23 相等（build 37）
```

### 3.3 反例

| ❌ | 问题 |
|---|---|
| `update` | 什么都没说 |
| `fix bug` | 哪个 bug |
| `修改了一些问题` | 无法检索、无法回滚判断 |
| `优化` | 优化了什么指标？前后对比？ |
| `更新基准文件` | **最危险的一类** —— 基准变动等于行为变动，必须解释哪一项变了、为什么 |

### 3.4 为什么"根因"必须写

三个月后你会问"为什么这段代码这么写"。
如果提交信息里有根因，答案就在 `git log` 里；
如果没有，你只能重新调试一遍——而且很可能再次踩同一个坑。

## 4. 一次提交改一件事

| 做法 | 结果 |
|---|---|
| 一个提交 = 一个逻辑改动 | 出问题能精确定位、能单独回滚 |
| 一个提交 = 五个改动 | 无法归因；回滚会波及其他 |

**例外**：同一个改动的"代码 + 对应文档 + 测试断言 + 基准更新"应当放在同一个提交里
（否则历史里会出现"文档描述了不存在的行为"的中间状态）。

## 5. 分支与推送

### 5.1 分支模型（个人 / 小团队）

```
master          稳定线，只接受"已验证"的合并，不直接开发
feature/<主题>  所有开发在这条线上
```

规则：
- `master` 上的每个提交都应该是"可安装、可用"的
- 大改动（多阶段）在 feature 分支走完，何时合并由负责人决定
- **决定不合并时也要写下来**（在 `01_项目进度` 或 `00` 里记录决策与理由）

### 5.2 推送策略

- 每个"阶段完成"或"重要修复"后推送
- 推送失败（网络/TLS）时**重试**，不要跳过（本地提交不算交付）
- 推送前确认 `git status` 干净（无未提交改动）

### 5.3 里程碑标签

```bash
git tag -a v0.4-S4 -m "S4 完成：诊断层，诊断集合与 CLI 23/23 相等，build 37"
```

标签信息里写**可验证的成果**，不要只写版本号。

## 6. 提交前检查清单

```markdown
- [ ] tsc 0 error 0 warning
- [ ] eslint 0 warning
- [ ] 单元测试全过
- [ ] golden 基准全过，且本次变动可解释
- [ ] 文档检查 PASS
- [ ] BUILD_ID 已递增（若有可加载改动）
- [ ] 相关文档已同步（进度表 / 架构文档 / 参数表自动重生成）
- [ ] 提交信息含"问题/根因/修法/验证"
- [ ] 一次提交只包含一个逻辑改动
- [ ] 已推送
```

---

## 7. 回滚规范

出问题时：

1. **先记录现象**（回滚会破坏现场）
2. 用 `git revert`（而不是 `reset --hard`）保留历史
3. 回滚提交里写明"回滚什么、为什么、后续如何处理"
4. `BUILD_ID` 继续递增（回滚也是一次可加载改动）
5. 在 `90_已知问题` 里登记该问题（避免再次尝试同样的方案）

## 8. 自动化：`verify.sh`

把三方验证写成一个脚本，一条命令跑完：

```bash
#!/usr/bin/env bash
set -e

echo "== 环境自证 =="
echo "node : $(node -v)"
echo "tsc  : $(npx tsc -v)"
echo "vscode: $(cat .vscode-version 2>/dev/null || echo '未锁定')"

echo "== 1/4 静态检查 =="
npx tsc --noEmit
npx eslint . --max-warnings=0

echo "== 2/4 单元测试 =="
npx vitest run

echo "== 3/4 基准回归 =="
node test/golden/run.js

echo "== 4/4 文档检查 =="
python test/doc_check.py

echo "ALL GREEN"
```

**规则：`verify.sh` 不绿就不许提交。**

### 8.1 调用方式必须写死

验证脚本最大的隐患是"跑在错误的环境里"：
同一个脚本，用不同的 shell / 不同的 node 版本跑，可能一个报"找不到模块"、
一个报"缺编译产物"——而真正的错误被掩盖。

要求：

| 要求 | 做法 |
|---|---|
| 固定 Node 版本 | `.nvmrc` + `package.json` 的 `engines` |
| 脚本自证环境 | 开头打印 node / tsc / 工具链版本 |
| 失败即停止 | `set -e` |
| 输出可判定 | 只输出关键行（`0 error`、`failed: 0`、`PASS`、`ALL GREEN`） |

### 8.2 基准变动必须人工过目

`verify.sh` 里有一步**故意不自动化**：基准文件的更新。

```
test/golden/run.js      → 只比对，永不自动更新
test/golden/run.js -u   → 人工确认后手动执行，且必须进同一个提交
```

理由：如果 CI 红了就自动 `-u`，基准就退化成"当前实现的复印件"，失去防回归能力。
