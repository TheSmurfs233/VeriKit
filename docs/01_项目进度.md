# 项目进度

> 最后更新：2026-11-08 · v0.3.5 build 18

## 1. 总体目标

做一个 VSCode 插件，解决 Verilog **代码编写**过程中的不便：高亮、语法检查、补全导航、片段、格式化、一键例化、模块树、端口提示。
**不做综合、不做仿真运行、不做工程生成。**
要求：轻量、跨平台（先只测 Windows）、仅自用。

## 4. 已知限制

1. `xvlog` 只做编译、不做 elaborate：**不报**跨文件模块未找到，也**发现不了**端口/位宽不匹配；这类检查需要 `xelab`（当前不做）
2. xvlog 冷启动耗时粗估 1~3 s，是"保存后出红线"的体验天花板（待实测）
3. 只实测 Windows；Linux / macOS 仅做 mock 覆盖

## 7. 决策记录

| 日期 | 决策 | 理由 |
|---|---|---|
| 2026-11-08 | 流程规范由嵌入式版改造为软件工程版 | 原版 04/06/07 的案例与工具全部是 STM32 绑定，需替换为软件域等价物 |
| 2026-11-08 | 不做 LSP，直接用 vscode API | 只服务 VSCode 一个编辑器，LSP 的"跨编辑器复用"收益为 0，且必然引入常驻进程 |
| 2026-11-08 | 语法检查包装外部 CLI（xvlog 优先） | 复用已有工具链，不自己写编译器前端 |
| 2026-11-08 | 格式化包装外部 formatter | 自己写能正确处理注释的 Verilog pretty-printer 是数月工作量 |
| 2026-11-08 | 只自研"模块头解析"一块 | 8 个需求里 7 个可外借；自研集中在"模块树/例化/端口提示/模块名补全"的公共内核 |
| 2026-11-08 | 补全第一版只做"模块名补全" | 语义补全需要完整 AST + 类型推断，成本高一个数量级；HDL 里 90% 的补全需求是"要例化某模块" |
| 2026-11-08 | 触发策略：默认"打开 + 保存"，编辑防抖默认关 | xvlog 每次起进程成本高；预留 `realtime` 模式，表驱动实现 |
| 2026-11-08 | 运行时依赖 = 0 | 体积、供应链、可测性三重考虑 |
| 2026-11-08 | 跨平台只实测 Windows | 仅自用，无其它平台机器；代码层面仍按跨平台写 |
| 2026-11-08 | 常驻进程：默认不启用，启用需满足五条规则 | "无感"才是真目标，"0 常驻"是手段；判据 = 1000 文件全量索引 > 1 s |
| 2026-11-08 | 高亮**先自写"够用子集"**，暂不 vendor 开源 grammar | 原判断"从零写要数周"针对的是**完整** grammar；本次只覆盖 11 类结构（注释/字符串/编译指令/模块头/关键字/类型/数字/系统任务/运算符/边沿/标点），约 90 行，**license 干净且可回归**。若日后发现覆盖不足，再考虑引入 MIT 的完整实现 |
| 2026-11-08 | 语法检查（S4）**押后**，先做高亮（S2） | 用户要求先出最基础的可见功能；S1/S1.5 已把探测与"原始检查"打通，随时可续 |
| 2026-11-08 | 定名 **VeriKit**（`verikit.*` 前缀） | 中性可扩展；必须在 S1 写首批配置键之前定死，否则改名会让旧配置静默失效 |
