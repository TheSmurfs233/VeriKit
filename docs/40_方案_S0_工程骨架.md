# S0 工程骨架 方案

> 日期：2026-11-08 · 状态：**已完成并通过手动验收（v0.0.2 build 2）** · 实际工期：约 2 小时
> 本阶段不写任何功能代码，只建立"改坏了能立刻知道"的能力。

---

## 1. 背景

项目当前只有 `workflow/` 规范文档，**没有任何代码、没有 git、没有 docs**。8 个需求中 7 个靠外借，1 个自研（模块头解析）。

在写第一个功能之前必须先解决一个更基础的问题：**改坏了能不能立刻知道？**

三个具体理由：

1. **自研那块的错误是静默的。** 模块头解析少认一个端口不会报错，只会让例化出来的代码少连一根线 —— 综合工具可能只是给个 warning，甚至没有。没有基准回归，这类 bug 会一直活在代码里。
2. **手动验证太贵。** 插件的一次手动验证 ≈ 50 秒（改码 + 编译 + 重载窗口 + 手点），而且不可重复。8 个功能 × 每个改 50 次 ≈ 一整天纯手点。
3. **门禁现在是空的。** workflow 要求"三方验证才提交"，而这三条现在一条都不存在。

| # | 目标 | 验收标准 | 级别 | 测法 |
|---|---|---|---|---|

## 4. 技术路线

### 4.1 方案选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 手写骨架** | 只有真正需要的 8 个文件，零清理成本；能说清每个字段为什么存在 | 需要知道每个字段含义 | ✅ **采用** |
| B. `yo code` 脚手架 | 一键生成 | 带 webpack、hello world 命令、示例测试；**清理成本 > 手写成本**，且我们要 esbuild 不是 webpack | ❌ 不采用 |

### 4.2 关键设计

**目录结构**

```
plugin/
├── src/
│   ├── extension.ts           激活入口：只做装配，不放业务逻辑
│   ├── core/                  ★ 禁止 import vscode
│   │   └── version.ts         BUILD_ID 唯一来源
│   └── vscode/                适配层：命令、输出通道、状态栏
├── grammars/                  （S2 填充）
├── snippets/                  （S2 填充）
├── test/
│   ├── unit/                  vitest 用例
│   ├── golden/corpus/         （S2 起）
│   ├── golden/expected/       （S2 起）
│   ├── arch.js                ★ 架构约束检查
│   └── doc_check.py           文档一致性检查
├── docs/                      5 份核心文档 + 本方案
├── esbuild.js
├── verify.sh
├── package.json
├── tsconfig.json
├── eslint.config.js
└── .vscodeignore
```

**三条结构约束（S0 就要立住，否则后面改不动）**

| # | 约束 | 强制执行方式 |
|---|---|---|
| 1 | `src/core/**` 不得 import `vscode` | `test/arch.js` 扫描，进 `verify.sh` |
| 2 | `extension.ts` 只做装配（注册命令/监听），不放业务逻辑 | 人工评审 + 后续拆分 |
| 3 | `BUILD_ID` 只在 `src/core/version.ts` 定义一次 | `doc_check.py` 校验 |

**为什么第 1 条这么重要**：一旦某个模块 `import vscode`，它就只能跑在扩展宿主里，永久失去在 vitest 中测试的可能。这条约束退化的过程是无声的 —— 某天为了图方便 import 一下，三个月后整个 `core/` 都不可测了。

### 4.3 外部依赖

**运行时依赖：0 个。** 全部用 Node 内置模块 + `vscode` API。S0 不接任何外部工具链。

### 4.4 关键参数（初值）

| 参数 | 初值 | 依据 |
|---|---|---|
| `version`（semver） | `0.0.1` | 骨架阶段，无功能 |
| `BUILD_ID` | `1` | 首个可被加载的版本 |
| `engines.vscode` | `^1.90.0` | 保守下限，覆盖近两年版本 |
| `@types/vscode` | 与 `engines.vscode` 同档 | **必须 ≤ engines.vscode**，否则用了不存在的 API |

## 6. 验证方法

| 项 | 级别 | 方法 | 期望 |
|---|---|---|---|
| 静态检查 | L1 | `tsc --noEmit && eslint . --max-warnings=0` | 0 error 0 warning |
| 单元测试 | L1 | `npx vitest run` | ≥ 1 passed |
| 架构约束 | L1 | `node test/arch.js` | 0 violation |
| 文档一致性 | L1 | `python test/doc_check.py` | PASS |
| 打包 | L1 | `npx vsce package` | 生成 `.vsix`，体积 < 5 MB |
| 激活 | L4 | F5 手动清单（见 §6.1） | 首行版本号正确 |

**`doc_check.py` 在 S0 只查 3 条**（其余随阶段增加）：

1. 版本号三方一致：`package.json` 的 `version` == `docs/01` 标题里写的版本；`BUILD_ID` 与 `docs/01` 里的 build 号一致
2. 表格列数一致性（报具体文件名 + 行号）
3. `@types/vscode` 的版本 ≤ `engines.vscode`

### 6.1 不做自动化的部分及理由

| 项 | 理由 | 补偿措施 |
|---|---|---|
| **L3 集成测试** | S0 只有一个占位命令，没有值得验的接线；引入 `@vscode/test-electron` 会下载一份 VSCode，拖慢 S0 | 推迟到 S1；**S1 的验收标准里必须包含"命令注册能被集成测试发现"** |
| 激活日志的可见性 | 属于渲染层（面板是否弹出、首行是否被清掉） | 手动清单逐条打钩，结果记入 `00_开发日志` |

**S0 手动验收清单（L4）**

```
[ ] F5 后出现新窗口，标题栏含 "[Extension Development Host]"
[ ] 底部输出面板（Ctrl+Shift+U）右上角下拉框里能选到 "FPGA"
[ ] 选中 "FPGA"，首行 = fpga-plugin v0.0.2 build 2
[ ] 命令面板（Ctrl+Shift+P）输入 "FPGA" 能看到 "FPGA: 显示诊断信息"
[ ] 执行该命令，面板内容追加一组诊断信息（含 build / vscode / node / platform）
[ ] 回到开发宿主窗口，修改 src/extension.ts 并 Ctrl+R 重载，命令仍可执行
[ ] 关闭窗口，OutputChannel 内容无异常报错
```

> **为什么要 `activationEvents: ["onStartupFinished"]`**：
> 只写 `contributes.commands` 时，VSCode 自动推导出的激活事件是 `onCommand:...` ——
> **插件要等你第一次执行命令才加载**，所以在那之前输出面板里根本不存在 "FPGA" 这个频道。
> 而本项目要求"每次会话第一行都有版本号"，所以必须开局就激活。
> 代价：每个窗口启动时多加载一次插件，激活体只有两行日志，可忽略。

> **与方案的偏差（已记录）**：原第 4 条写的是"重载后日志只有一行（验证 dispose 是否干净）"。
> 实际不可行 —— OutputChannel 在重载时随扩展宿主重建，历史内容本就清空，观测不到重复注册。
> **S0 没有任何长生命周期对象，dispose 正确性在 S0 无法观测**，推迟到 S1（有了文件监听和状态栏之后再验）。

### 6.2 会写用户文件的部分

**无。** S0 不写任何用户工作区文件，不启动任何外部进程。

## 7. 风险与对策

| # | 风险 | 可能性 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | `@types/vscode` 与 `engines.vscode` 不匹配 | 中 | 编译通过但运行时 API 不存在，激活即崩 | `doc_check.py` 增加第 3 条比对 |
| 2 | `core/` 被悄悄塞进 vscode 依赖 | **高**（随项目变大必然发生） | 该模块永久失去单测能力 | `test/arch.js` 进 `verify.sh`，每次提交都跑 |
| 3 | `doc_check.py` 一开始写太复杂 | 中 | 写不完，或写完长期红着没人管 | S0 只查 3 条；宁少勿多 |
| 4 | Windows 下中文路径 / 编码问题 | 中 | 乱码、脚本误报 | 所有文件 UTF-8 无 BOM；路径一律走 `node:path` |
| 5 | 首次 F5 失败（`launch.json` 配错） | 中 | 卡在环境上耗掉半天 | 严格按序：先 `tsc` 过 → 再 F5；`launch.json` 用最简配置 |
| 6 | esbuild 产物没被 `main` 正确指向 | 中 | 激活报 "Cannot find module" | `.vscodeignore` 与 `main` 字段交叉验证；打包后手动装一次 vsix |

### 9.1 与方案的偏差

| 项 | 方案 | 实际 | 原因 |
|---|---|---|---|
| 测试配置文件 | `vitest.config.ts` | `vitest.config.mts` | `.ts` 在无 `"type":"module"` 的包中按 CJS 加载，触发 Vite CJS 弃用警告；改 `.mts` 后警告消失 |
| 配置内容 | 含 `diff: { expand: true }` | 移除该项 | 该选项在本机 vitest 2.1.9 上导致启动崩溃（`normalizeWindowsPath: input.replace is not a function`），已实测确认是它引起 |
| `verify.sh` 分段 | 静态/测试/架构/文档/打包 | 静态/测试/架构+文档/构建/打包 | 打包前必须先构建，否则 vsix 里没有 `dist/extension.js`；架构与文档合并为一段 |
| dispose 验证 | 重载后日志只一行 | 改为"重载后命令仍可执行" | OutputChannel 随宿主重建，原判据不可观测（详见 §6.1） |
