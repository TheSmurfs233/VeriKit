## 2. 设计限制（不是 bug，但要知道）

| # | 限制 | 原因 | 影响面 |
|---|---|---|---|
| 1 | **`xvlog` 不做 elaborate，因此不报"跨文件模块未找到"** | 实测：`top.v`（例化了 `counter`）单独交给 xvlog，只输出 2 行 INFO、**无任何错误**。模块解析发生在 `xelab` 阶段 | 单文件语法检查是**安全的**、不需要 filelist；但反过来，**跨文件的端口/位宽不匹配也查不出来** —— 那属于 elaborate |
| 2 | **诊断定位精度上限是"整行"** | xvlog / vlog / iverilog 的常规输出都只给行号，不给列号 | 编辑器里只能整行标红，无法精确到 token |
| 3 | ~~只支持 ANSI 端口写法~~ → **大部分已解除**（v0.11.3） | 非 ANSI 模块的体内端口声明已并入索引（`collectBodyPorts`）：方向提示/端口补全/一键例化对非 ANSI 模块生效 | 残留：如需**位宽/参数默认值**的结构化细节仍需头解析；legacy 样本验证通过 |
| 4 | 不展开宏位宽 | `[`WIDTH-1:0]` 原样保留文本 | 例化输出里带宏，可读性依赖用户工程 |
| 5 | `generate` 内的模块实例不进模块树 | 模块树只管"模块定义"，不管"实例" | 用 `generate` 组织的大型工程，模块树不代表实际层次 |
| 6 | 跨平台仅实测 Windows | 仅自用，无 Linux/macOS 机器 | 换平台时 `.bat`、PATH、可执行位相关逻辑需重新验证 |
| 7 | 不做语义级补全 | 需要完整 AST + 类型推断 | 变量名/信号名补全缺失，只有模块名补全 |
| 8 | `eslint` 忽略所有 `.js` 文件 | 为 `esbuild.js`、`test/arch.js` 两个几十行脚本引入 `globals` 依赖，违背运行时零依赖原则 | 这两个脚本没有静态检查，只能靠它们自身运行来验证（`arch.js` 的退出码会被 `verify.sh` 检查） |
| 9 | **`xvlog` 一次调用约 1 s（实测）** | PowerShell 侧：首次 2016 ms，连续三次 1002 / 977 / 1022 ms；**插件内实测版本查询 881 ms**，与前者吻合 | 所有调用必须缓存 + 懒执行；S4 的"编辑时触发"应**彻底移除**而非"默认关闭" |
| 10 | **`xvlog -version` 也会在 cwd 留文件** | 实测在 cwd 产生 `xvlog.log` 与 `xvlog.pb` | 所有调用（含版本查询）都必须以临时目录为 cwd，结束后清理 |
| 11 | 探测结果不持久化 | 目前只在内存里缓存，重载窗口后要重新探测（约 1 s） | 重新加载窗口后首次点状态栏会等约 1 s；若要持久化可用 `context.globalState` |

## 5. 平台差异

| # | 平台 | 现象 | 判断依据 | 处理 |
|---|---|---|---|---|
| 1 | Windows | `xvlog` 只有 `.bat`，直接 `spawn` 会 ENOENT | 命令行可跑、插件内报错 | 解析 `.exe`/`.cmd`/`.bat`，`.bat` 走 `cmd /c` |
| 2 | Windows | xvlog 在 cwd 生成 `xsim.dir/`、`xvlog.log`、`xvlog.pb` | 用户工程目录出现多余文件 | 以临时目录为 cwd，路径全传绝对路径，结束后清理 |
| 3 | Windows | `-work work=<path>` 写法在部分版本上导致"完全没有诊断输出" | 参考 mshr-h 的实现说明 | 不注入 `-work` 参数 |
| 4 | 全平台 | 从桌面图标启动的 VSCode 的 PATH ≠ 终端 PATH | 终端能跑、插件探测不到 | 允许配置绝对路径；探测失败时提示"请手动指定路径" |
| 5 | Linux / macOS | 工具无扩展名或缺可执行位 | 探测返回不可用 | 提示 `chmod +x` 或手配路径（**未实测**） |
| 6 | Windows | PowerShell 里敲 `npm` 报"禁止运行脚本"（`npm.ps1` 被策略拦截） | 终端直接跑 `npm run x` 失败，但 Git Bash 里正常 | 用 Git Bash，或写 `npm.cmd run x`；项目内构建任务已改为直接 `node esbuild.js`，不经过 npm |
| 7 | Windows | **同一文件的盘符大小写与分隔符不一致**：`document.fileName` 给 `d:\Embedded\...`，xvlog 回显 `d:/Embedded/...` | 实测同一次检查里两种写法同时出现 | **所有路径比较必须 `toLowerCase()` + 分隔符归一**；否则 S4 会把诊断匹配不到文件而静默丢弃 |

## 3. xvlog 版本兼容矩阵（2026-11-08 采集）

**结论：设计兼容 2019.2 ~ 2026.x；实测 2022.2。换机/升级后跑一次「VeriKit: 解析器自检（版本兼容）」当场验证。**

插件对 xvlog 的全部依赖面只有 4 项，均为跨版本稳定面：

| 依赖面 | 用途 | 2019~2026 稳定性 |
|---|---|---|
| `bin/xvlog.bat` 存在 | 调用入口（路径布局 <root>/<ver>/bin 不变） | ✅ |
| `--version` | 探测与版本显示 | ✅ |
| 单文件裸编译（无 flag） | lintFileRaw（临时目录隔离污染） | ✅ |
| 消息格式 `SEVERITY: [VRFC 10-x] msg [file:line]` | 解析器 | ✅ 核心格式；**新增行形态由自检哨兵暴露**（dropped.other） |

已内置的防线：
- 错误码透明捕获（不依赖具体码值，跨版本码值会变）
- 临时目录隔离（xvlog.log / xsim.dir 污染不进工程）
- INFO 行无 [文件:行] 尾缀已兼容（fixture 抓过这个真 bug）
- 解析自检哨兵 + `VeriKit: 解析器自检（版本兼容）` 命令

剩余风险（均为**显示退化**级别，不会崩溃）：
- 新版本引入全新消息形态 → 哨兵告警，需按新样本扩展解析器
- 版本横幅格式变化 → 仅状态栏版本显示
- 老系统编码差异（GBK）→ 仅消息文本可能乱码，[file:line] 为 ASCII 不受影响
