# S4 语法检查 方案

> 日期：2026-11-09 · 状态：**✅ 完成（onOpenSave + onEdit 双模式）** · 8 步全部落地

---

## 1. 背景

S1.5 已经能"对当前文件跑一次 xvlog 并原样打印"。S4 要把这条链路变成**编辑器里看得见的结果**：

- 打开/保存 `.v` 时自动检查
- 结果画成红线，落在正确的位置
- 不出假红线、不留旧红线、不因为快速保存而错位

三个前置事实（都已实测，不是假设）：

| 事实 | 影响 |
|---|---|
| 单次调用 **0.8~1.3 s**（随缓存波动） | 触发策略只能"打开 + 保存"，`onEdit` 必须移除 |
| 输出里 **INFO 行占一半**（4 行里 2 行是 INFO） | 不滤掉就是假红线 |
| 路径写法不一致：`d:\...` vs `d:/...` | 不做归一 → 诊断静默丢失，且无报错 |

## 3. 非目标（S4 不做）

| 不做 | 原因 |
|---|---|
| `onEdit`（编辑时触发） | 单次 1 s 级；8 条结论里已定"彻底移除"而非默认关闭 |
| 跨文件 elaborate（端口/位宽不匹配） | 需要 `xelab`，是另一个量级的功能；当前 `xvlog` 阶段做不到 |
| filelist（`.f`） | 实测 `xvlog` 不报跨文件模块未找到，**不需要** |
| ModelSim / Icarus 适配 | 接口已留（`ToolAdapter`），S4 只做 xvlog |
| Quick Fix / 代码操作 | 属于编辑增强，不在语法检查范围 |
| 全工程批量检查 | 需要索引（S3）与并发控制，留给以后 |

## 4. 技术路线

### 4.1 解析器（纯函数，先于实现写测试）

```ts
// core/diag/parse.ts
export type DiagSeverity = 'error' | 'warning';

export interface DiagItem {
  file: string;      // 原样保留 CLI 给的路径（可能是 d:/...）
  line: number;      // 1-based
  code: string;      // 'VRFC 10-4982'
  message: string;
  severity: DiagSeverity;
}

export interface ParseResult {
  items: DiagItem[];
  dropped: { info: number; other: number };   // 被丢弃的行数，用于日志
}

export function parseXvlogOutput(text: string): ParseResult;
```

正则（已由真实输出确定）：

```
^(ERROR|WARNING|INFO):\s*\[([A-Z]+ [\d-]+)\]\s*(.*?)\s*\[(.+):(\d+)\]\s*$
```

- **只收 ERROR / WARNING**；INFO 计入 `dropped.info`
- 不匹配的行计入 `dropped.other`（**不静默吞掉**，否则解析器退化了也看不出来）
- 行号 1-based；无列号 → `Range` 的列填 0

**验收用 fixture 而不是手编样本**：`test/fixtures/xvlog/*.stdout.txt` 已入库 4 个真实样本。

### 4.2 路径归一（这是最容易静默失败的一环）

```ts
// core/path/normalize.ts
export function normalizeFsPath(p: string): string {
  return p.replace(/\\/g, '/').toLowerCase();
}
```

实测同一次检查里出现两种写法：

```
document.fileName : d:\Embedded\FPGA\...\broken.v
xvlog 回显        : d:/Embedded/FPGA/.../broken.v
```

**若直接字符串比较，诊断会匹配不到文档 → 全部丢弃，且没有任何报错。** 这是 S4 最大的静默失败风险。

对策：
1. 解析出的 `file` 归一
2. 在"已打开文档"里按归一路径找；找不到则 `Uri.file(file)`
3. 单测必须覆盖三种写法：`d:\a\b.v`、`D:/a/b.v`、`d:/A/B.v`

### 4.3 诊断写入

```
DiagnosticController（全项目唯一 owner，唯一持有 DiagnosticCollection）
```

| 场景 | 动作 |
|---|---|
| 正常更新（同一文件） | `collection.set(uri, newDiags)` —— **替换，不清空**，避免闪烁 |
| 文件被关闭 | `collection.delete(uri)` |
| 工具链缺失 / 切到 none | `collection.clear()` —— 整簇清空，不留残迹 |
| 检查超时 | `collection.delete(uri)` + 日志说明（不展示过期结果） |

`source: 'verikit'`，便于用户在问题面板按来源过滤。

### 4.4 触发

| 事件 | 是否触发 |
|---|---|
| `onDidOpenTextDocument` | ✅（仅 `.v`） |
| `onDidSaveTextDocument` | ✅（仅 `.v`） |
| `onDidChangeTextDocument` | ❌ 不做 |
| 命令 `检查当前文件` | ✅（复用同一执行路径） |

由 `core/trigger/policy.ts` 的表驱动实现（`onOpenSave` 模式），为将来加模式留口子。

### 4.5 竞态保护

每个文档维护：

```ts
interface DocState {
  seq: number;                 // 每次发起 +1
  inFlight?: AbortController;  // 新请求先取消旧的
}
```

- 结果返回时比对 `seq`，过期直接丢弃（不写诊断）
- 日志打印 `seq`，便于复盘"为什么显示的是旧结果"

### 4.6 降级

| 情况 | 行为 |
|---|---|
| 未找到工具链 | 清空所有诊断；状态栏 `⚠ VeriKit`；日志说明 |
| `verikit.toolchain = none` | 同上，状态栏 `⊘ VeriKit` |
| 进程超时 | 删除该文件诊断；日志记 `timedOut` |
| 解析出 0 条但日志有 ERROR 行 | **日志警告"疑似解析器退化"** —— 这类静默失败必须能自查 |

最后一条是给未来的自己留的保险：**如果 `parseXvlogOutput` 因为格式变化丢了解析，`dropped.other > 0` 会暴露它**。

### 4.7 关键参数

| 项 | 值 | 说明 |
|---|---|---|
| 诊断来源 | `verikit` | 问题面板可过滤 |
| severity 映射 | ERROR→`Error`、WARNING→`Warning` | INFO 不入诊断 |
| 列号 | 固定 0 | xvlog 不提供列号 |

## 5. 实施步骤

| 步 | 内容 | 产出 |
|---|---|---|
| 1 | `core/path/normalize.ts` + 单测（三种写法） | 路径归一 |
| 2 | `core/diag/parse.ts` + fixture 回归（4 样本，L2） | 解析器 |
| 3 | `core/diag/toVscode.ts`：`DiagItem → vscode.Diagnostic`（纯映射，但需要 Range → 放 vscode 层） | 映射 |
| 4 | `vscode/diagnosticController.ts`：唯一 owner + 整簇/替换语义 | 写入 |
| 5 | `core/trigger/policy.ts` + `vscode/triggerScheduler.ts`：表驱动 + 序号 + 取消 | 触发 |
| 6 | 接入 `onDidOpen/onDidSave`，与命令复用同一路径 | 联动 |
| 7 | 降级路径（none / 缺失 / 超时 / 解析异常自检） | 降级 |
| 8 | 手验 8 条目标 + 更新 `01` / `90` | 收尾 |

**步 1、2 必须先做**：它们能在完全没有 VSCode 的情况下跑通，是整段最省力的部分。

## 6. 验证方法

| 项 | 级别 | 方法 | 期望 |
|---|---|---|---|
| 路径归一 | L1 | 三种写法互比 | 归一后相等 |
| 解析器 | L2 | 4 个 fixture | broken=2 条、其余=0 条；`dropped.info=2` |
| 触发策略 | L1 | 表驱动枚举（事件 × 模式） | 只有 open/save 返回 true |
| 竞态 | L1 | 模拟 seq 递减返回 | 过期结果不写入 |
| 端到端 | L4 | 保存 `broken.v` | 2 条红线在第 7 行 |
| 降级 | L4 | 切 `none` | 红线消失 + 状态栏提示 |

### 6.1 不做自动化的部分及理由

| 项 | 理由 | 补偿 |
|---|---|---|
| 红线"看起来对不对" | 渲染层 | 手动清单逐条打钩 |
| 真实耗时 | 随机器负载波动 | 只记录不设门槛 |
| 闪烁 | 属观感 | 手验连续保存 5 次观察 |

### 6.2 会写用户文件的部分

**无。** 所有检查在临时目录进行，不写工作区。

## 7. 风险与对策

| # | 风险 | 可能性 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | 路径匹配失败 → 诊断全丢且无报错 | **高** | 功能看起来"完全没反应" | 路径归一 + L1 单测 + 日志打印解析到的 uri |
| 2 | 解析器对格式变化不敏感，静默丢诊断 | 中 | 部分错误不显示 | `dropped.other` 计数 + 超过阈值时日志告警 |
| 3 | 首个语法错误掩盖后续（实测 `broken.v` 只报第 7 行） | 必然 | 用户以为"只有一个错" | 写进 `90` 设计限制；不在 UI 上承诺"全部错误" |
| 4 | 诊断闪烁 | 中 | 观感差 | 正常更新用 `set` 替换，不用 `clear` |
| 5 | 大文件耗时增加 | 低 | 保存后等待变长 | 记录耗时；超过 3 s 时状态栏提示"检查中" |

  功能降级为"手动看原始输出"，不影响其他能力

## 10. 需要确认的两件事（已确认并落地）

1. **触发只做"打开 + 保存"** —— ✅ 已确认。"编辑时检查"由用户追加提问，答复：技术上可行，
   但 xvlog 读磁盘文件，未保存内容需先写临时文件，且每次约 1 s CPU；方案为后续可选配置
   （`verikit.check.onEdit`，默认关），作为 S4 之后的增量，走同一管道。
2. **不承诺"列出全部错误"** —— ✅ 已确认。`xvlog` 在首个语法错误后中止解析是工具行为。
   补偿：修一个错保存后自动重查下一个；输出日志注明每轮诊断条数。
