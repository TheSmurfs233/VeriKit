## 2026-11-08 · 修门禁偶发失败（vitest 并行抢写临时缓存）

### 背景

提交上一条文档时，`bash verify.sh | tail` 的退出码被管道吞掉了，实际没发现门禁已经红了。
改用不带管道的方式复核后，发现单测是**间歇性失败**。

### 数据

| 试验 | 结果 |
|---|---|
| `vitest run` 连跑 3 次 | exit 0 / **exit 1** / **exit 1**（3 次里 1 次过） |
| 失败时的报错 | `EPERM: operation not permitted, open 'C:\...\Temp\-a1iA4...\ssr\40b9f1f3...'` |
| 失败时的用例数 | 只剩 6 个文件（正常 7 个）—— 有一个文件加载失败 |
| `vitest run --no-file-parallelism` 连跑 5 次 | **5/5 exit 0** |
| 改配置后 `bash verify.sh` 连跑 3 次 | **3/3 ALL GREEN** |

### 分析

- 报错路径里的 `ssr\<hash>` 是 **Vite 的 SSR 转换缓存**，落在系统临时目录；同一 hash 每次相同，父目录随机 → 是"同一份缓存被并发写"。
- 根因是 **vitest 默认按文件并行**，多个 worker 同时写这份缓存；Windows 上文件被占用即 `EPERM`。
- 这类失败最伤信任：**代码一行没改，门禁却红了**。按 `workflow/08` 的说法，这正是"`verify.sh` 总失败就不管了"的前兆，必须修而不是重跑。
- 修法选串行而不是调缓存路径：本套用例总耗时 1~2 s，串行代价可接受；调 Vite 内部缓存路径属于和工具实现耦合，容易随升级失效。

### 结论与动作

| # | 动作 |
|---|---|
| 1 | `vitest.config.mts` 增加 `fileParallelism: false`，并写清原因与实测数据 |
| 2 | 记入 `90` §4 第 5 条 |
| 3 | 自查操作习惯：**`bash verify.sh \| tail` 会吞掉退出码**，以后要么不接管道，要么显式 `echo exit=$?` |
| 4 | 本次只改测试配置，按规则**不递增 BUILD_ID** |

### 验证

| 项 | 结果 |
|---|---|
| `vitest run` 串行 | 5/5 exit 0 |
| `verify.sh` 连跑 3 次 | 3/3 ALL GREEN |

### 遗留

- [ ] 无

## 2026-11-08 · 实测推翻"xvlog 单文件必然误报"的判断，并摸清诊断格式

### 背景

用户问："目前 xvlog 的语法检查有作用么，还是只停留在工具查找与选择上？"
答案是没有做检查。既然要回答，就顺手用 `test-workspace` 的三个文件真跑一遍 ——
这也正好是 S4 需要的 fixture 来源。

### 数据

在临时目录里分别对三个文件跑 `xvlog.bat <绝对路径>`：

| 文件 | 耗时 | 输出 | cwd 残留 |
|---|---|---|---|
| `counter.v`（正常模块） | 1159 ms | 2 行 INFO，无错误 | `xsim.dir`, `xvlog.log`, `xvlog.pb` |
| `broken.v`（2 处故意语法错） | 1072 ms | 2 行 INFO + **2 行 ERROR（都在第 7 行）** | 同上 |
| `top.v`（例化 `counter`，跨文件） | 1097 ms | 2 行 INFO，**无任何错误** | 同上 |

原始输出（`broken.v`）：

```
INFO: [VRFC 10-2263] Analyzing Verilog file ".../broken.v" into library work
INFO: [VRFC 10-311] analyzing module broken
ERROR: [VRFC 10-4982] syntax error near 'input' [.../broken.v:7]
ERROR: [VRFC 10-8549] Verilog 2000 keyword 'input' used in incorrect context [.../broken.v:7]
```

### 分析

- **假设被推翻**：此前我判断"单文件检查会把跨文件例化报成 `VRFC 10-2063 Module <x> not found`"，
  并据此提出 S4.5（`.f` 文件清单）。
  **实测 `top.v` 单独编译零错误** —— 因为 `xvlog` 只做**编译**，模块解析发生在 **`xelab`（elaborate）** 阶段。
  单文件语法检查是安全的，**不需要 filelist**。
- **反向的代价**：既然不做 elaborate，也就**发现不了跨文件的端口/位宽不匹配**。这是能力边界，要写进已知限制。
- **诊断格式已确定**，可直接写解析器：
  `^(ERROR|WARNING|INFO): \[VRFC (\d+-\d+)\] (.*?) \[(.+):(\d+)\]$`
  - 只有行号，**没有列号**（与之前判断一致）
  - `INFO` 行不是诊断，必须过滤掉
  - 路径可能含空格与中文，且是正斜杠
- **一次真实检查约 1.1 s**（与 `-version` 的 881 ms 同量级）—— 说明耗时主要来自工具启动，不是文件大小。
- **`broken.v` 只报了第 7 行**：缺分号那处（第 15 行附近）没被报出来，因为解析在首个语法错误后中止了。
  所以"诊断条数"不等于"错误总数" —— 修完一个才会暴露下一个。
- 残留物比预想的多：除了两个文件，还有一个 **`xsim.dir` 目录**。

### 结论与动作

| # | 动作 |
|---|---|
| 1 | `90` §2 第 1 条改写：xvlog 不 elaborate → 不报跨文件模块未找到；但跨文件语义也查不出来 |
| 2 | `01` 阶段表：S4.5（`.f` 清单）标为 **❌ 不需要** |
| 3 | `01` 已知限制第 1 条改写为"能力边界"而非"误报" |
| 4 | `18` 第 3 项：filelist 仅在将来接 `xelab` 时才需要 |
| 5 | 这批真实输出直接作为 S4 的诊断解析 fixture（三种样本：干净 / 语法错 / 跨文件） |

### 验证

| 项 | 结果 |
|---|---|
| 三个文件均能正常返回 | ✅ 1061~1159 ms |
| 诊断格式 | ✅ 已确定正则，含行号、无列号、多行 INFO 需过滤 |
| 跨文件是否误报 | ✅ **不误报**（推翻原假设） |
| cwd 污染 | ✅ 确认产生 `xsim.dir` / `xvlog.log` / `xvlog.pb` |

### 遗留

- [ ] **语法检查功能尚未实现**（S4 才做）：目前插件不会把任何文件送给 xvlog，编辑器里不会出现红线

## 2026-11-08 · 修 `.bat` 启动形态：版本查询 53 ms 失败（v0.1.1 build 6）

### 背景

S1 手动验收时，状态栏能显示 `xvlog`，但**没有版本号**。日志里这一行不对：

```
[probe] presence: found via path  D:\Xilinx\Vivado\2022.2\bin\xvlog.bat  (4 ms)
[probe] version: 未知  (53 ms)
```

53 ms 不可能跑完 `xvlog`（此前实测约 1000 ms），说明进程几乎立刻退出了。

### 现象 / 问题

- 存在性探测正常（4 ms，走 PATH 命中）—— 顺带推翻了我之前"PATH 里没有 Vivado"的判断
- 版本查询失败，且日志里**没有原始输出**，只能去外部复现

### 数据

写了个临时脚本对比三种启动形态（目标 `xvlog.bat`，cwd 为临时目录）：

| 形态 | 结果 |
|---|---|
| A `cmd /d /s /c "path -version"`（原实现） | ❌ code=1, **50 ms**；stderr 是"`'\"D:\...\xvlog.bat -version\"'` 不是内部或外部命令" |
| B `cmd /d /s /c call path -version` | ✅ code=0, 1257 ms, `Vivado Simulator v2022.2` |
| C 直接 spawn `.bat` | ❌ `EINVAL` |

补充验证 B 在**路径含空格**时仍然正确：造了 `...\Program Files X\fake tool.bat`，
`call` 形态返回 `FAKE-OK hello`，code=0。

### 分析

- 根因是 **Node 的 argv 转义**：`spawn('cmd.exe', ['/d','/s','/c','"C:\\path\\x.bat -version"'])`
  里那个带引号的参数含有空格和引号，Node 会把它转义成 `\"...\"` 再拼到命令行上。
  cmd 收到的是**字面量反斜杠+引号**，于是把整串当成一个不存在的命令名。
- 我之前的设计假设是"手工拼一条 `/s /c "..."` 就能控制引号形态"——**这个假设错了**，
  而且纯函数单测测不出来：单测只验证我拼出来的字符串长什么样，验证不了 Node 最终交给系统的是什么。
- 正解是**不拼命令行**：把 `call` 作为 cmd 的命令、路径与参数各自作为独立 argv 交出去，
  加引号的活交给 Node 做（它对每个参数单独处理，含空格才加引号）。
- 另一处缺陷：**日志里没有原始输出**。53 ms 失败时，stdout/stderr 全是空的还是报错文本，
  日志没记，只能另写脚本复现。观测性不足导致多花了一轮。

### 结论与动作

| # | 动作 |
|---|---|
| 1 | `buildSpawnPlan` 改为 `['/d','/s','/c','call', target, ...args]`，不再手工拼引号 |
| 2 | 保留元字符校验（`& \| < > ^ "` 一律拒绝），因为我们确实要经过 cmd |
| 3 | **新增真实进程回归测试** `test/unit/winShim.spawn.test.ts`：造一个"目录名+文件名都带空格"的 `.bat`，用 `runCapture` 真跑一遍；再验非零退出码。平台门控 `describe.skipIf(!isWindows)` |
| 4 | `toolchainService` 在拿不到版本时**打印原始 code/stdout/stderr（截断 300 字）** —— 下次不用再写外部脚本 |
| 5 | 版本 `0.1.0 build 5` → **`0.1.1 build 6`** |

### 验证

| 项 | 结果 |
|---|---|
| `tsc --noEmit` | 0 error |
| `vitest` | **39 passed / 7 files**（新增的 `.bat` 真实进程用例包含在内） |
| 真实进程用例 | 含空格路径执行成功、输出 `MARK hello`、非零码返回 7 |
| `verify.sh` | ALL GREEN |

### 遗留

- [ ] 需再次手动验收：确认状态栏变成 `xvlog 2022.2`，且 `[probe] version: 2022.2 (约 1000 ms)`
- [ ] **教训入库**：`07_调试方法论` 的"判据不变量"原则在这里表现为 ——
      **"我拼出来的字符串"不是判据，"进程实际收到什么"才是**。已记入本条与 `90` 第 4 条

## 2026-11-08 · S1 实施：工具链探测 + 可观测（v0.1.0 build 5）

### 背景

S0 只建立了门禁。S1 要解决"看不见"：插件不知道 `xvlog` 在哪、能不能跑、跑一次多慢。
先做了方案里排第一的实测（探路），再按实测结果写代码。

### 现象 / 问题

步 1 的实测带来三个意外，都改变了实现：

| # | 发现 | 对实现的影响 |
|---|---|---|
| 1 | `xvlog.bat -version` 可用，输出 `Vivado Simulator v2022.2` | 版本分支保留，需要写解析器 |
| 2 | **首次 2016 ms，连续三次 1002 / 977 / 1022 ms** | 探测必须"快慢分离"：存在性检查走纯 fs（毫秒级），版本查询单独一步（约 1 s） |
| 3 | **只查版本也会在 cwd 留下 `xvlog.log` 与 `xvlog.pb`** | 临时目录做 cwd 不是只针对真正的编译，连 `-version` 都要 |

另外：`XILINX_VIVADO` 环境变量在本机**未设置**，所以三级级联的第三级（环境变量兜底）在本机走不到，
只能靠单测覆盖。

### 数据

| 项 | 值 | 来源 |
|---|---|---|
| 首次 `-version` | **2016 ms** | PowerShell 计时 |
| 连续三次 | 1002 / 977 / 1022 ms | 同上 |
| cwd 残留 | `xvlog.log`, `xvlog.pb` | 临时目录 `ls` |
| 单测 | **36 passed / 6 files** | `npx vitest run` |
| 新增单测文件 | expand / winShim / pathLookup / detect / runner | — |

### 分析

- **结论 1：存在性与版本必须拆成两次返回。** 若合并成一个 `ProbeResult`，状态栏要白等 1 s 才能显示
  "找到了"。拆开后状态栏能立刻显示路径，版本到了再补 —— 这也让失败场景（根本起不来进程）不必陪等。
- **结论 2：`onEdit` 触发策略在 S4 必须彻底移除，而不是"默认关闭"。** 1 s 的进程 + 持续打字 = 风扇常转。
  留一个默认关闭的选项，等于给未来的自己埋雷（"反正可以开"）。
- **结论 3：`.bat` 的 spawn 不能靠"试试看"。** 用纯函数 `buildSpawnPlan` 生成
  `cmd.exe /d /s /c "\"path\" args"`，并在单测里锁死含空格路径的引号形态 —— 这是最容易被"我这边能跑"掩盖的地方。
- **结论 4（检查规则的第二次修正）**：`doc_check` 上一轮已从"扫全部 docs"收窄到"扫 01/90"，
  但这两份文档内部**也有历史证据**（某阶段在哪个版本验收的）。本轮 `sed` 批量改版本号时，
  差点把"S0 在 v0.0.4 验收"这条历史改成"在 v0.1.0 验收"。
  → 规则再收窄一次：**只校验 `> 最后更新：… vX.Y.Z build N` 这一行**，其余一律视为历史，不改不校验。

### 结论与动作

| # | 动作 |
|---|---|
| 1 | 新增 `core/proc/{runner,winShim}.ts`：唯一 spawn 出口 + `.bat` 经 cmd 转发（引号形态有单测锁死） |
| 2 | 新增 `core/path/expand.ts`：`${env:VAR}` 与 `~` 展开，未定义变量展开成空串 |
| 3 | 新增 `core/toolchain/{adapter,pathLookup,detect,version}.ts`：三级级联 + `attempts[]` 记录每次尝试 |
| 4 | 新增 `vscode/toolchainService.ts`：状态栏 + 内存缓存 + 配置变更 300 ms 防抖重探；**activate 不探测** |

## 2026-11-08 · 改名 VeriKit（v0.0.3 build 3）

### 背景

OutputChannel 原来叫 `FPGA`，输出面板下拉框里跟别的插件分不清。要求改成插件名 —— 但插件名当时还没定。

### 数据

| 候选 | 含义 | 取舍 |
|---|---|---|
| **VeriKit** | Verilog 工具集 | ✅ **采用**：中性、可扩展，将来加功能不违和 |
| VeriScope | `scope` 双关（语法作用域 / 看清层次） | 语义最贴，但内涵偏"看"，限制后续扩展 |

- **另外暴露了一个检查规则的问题**：`doc_check.py` 原本扫描 `docs/*.md` 下**所有**版本号字符串，
  而本流程规定 `00_开发日志` 是追加式、永不改写历史条目。两者直接冲突 ——
  每次递增版本都要篡改日志才能过检查。这是检查规则设计错，不是日志写错。

### 结论与动作

## 2026-11-08 · S0 执行完成：骨架 + 五段门禁全绿（build 1）

### 背景

按 `docs/40_方案_S0_工程骨架.md` 执行 S0。本阶段目标只有一个：**建立"改坏了能立刻知道"的能力**，不写任何功能代码。

执行过程中撞到三个问题，按发现顺序：

1. `vitest run` 启动即崩，栈指向 `pathe` 的 `normalizeWindowsPath`。
2. **首次打包把 `.workbuddy/memory/2026-11-08.md` 打进了 vsix。**
3. 为防问题 2 复发而加的白名单检查，**自己的中间文件又被打进了包**。

### 数据

| 项 | 值 | 来源 |
|---|---|---|
| tsc | 0 error | `npx tsc --noEmit` |
| eslint | 0 warning | `npx eslint . --max-warnings=0` |

| 架构检查 | 0 violation / 1 个 core 文件 | `node test/arch.js` |
| 文档检查 | PASS | `python test/doc_check.py` |
| esbuild 产物 | 2.8 KB | `dist/extension.js` |
| vsix（**有泄漏**） | 7.8 KB / 6 文件 | 首次 `vsce package` |
| vsix（修复后） | **5.0 KB / 4 文件** | 最终 `vsce package` |

```
首次打包的文件清单：
   LICENSE.txt / package.json / readme.md
   dist/extension.js
   .workbuddy/memory/2026-11-08.md     ← 不该出现
```

### 分析

**问题 1（vitest 崩溃）**：报错栈指向 `pathe` 的路径归一化，看起来像 vitest 内部 bug。
用二分法：删掉整份 `vitest.config.ts` 后能跑 → 逐项加回 → 定位到 `test.diff = { expand: true }` 这一行。
同时 `.ts` 配置在没有 `"type": "module"` 的包里按 CJS 加载，会打印 Vite 的 CJS 弃用警告 —— 改名为 `.mts` 后一并消失。

> **教训**：栈指向哪里不等于根因在哪里。栈说的是"崩在字符串处理"，根因是"配置对象里的一个字段让某个路径参数变成了 undefined"。**顺着栈查库源码会走偏，二分才有效。**

**问题 2（vsix 泄漏）**：`vsce package` 打印了包含文件清单，读了一下才发现多了一项。
如果只看最后一行的 `DONE Packaged` 就提交，一份含个人项目记忆的文件就随安装包分发出去了。
根因：`.vscodeignore` 只写了常规排除项（`src/`、`test/`、`docs/`、`node_modules/`），**漏了工具目录 `.workbuddy/`**。

> **教训：打包成功 ≠ 打包正确。** 判据必须是"打进去了哪些文件"，而不是"打包命令有没有报错"。
> 这正是 `07` 里"不要用被验证对象验证它自己"的一个实例 —— `vsce` 的退出码不能证明内容正确。

**问题 3（检查脚本污染打包）**：为了把问题 2 变成断言，加了白名单检查，实现是
`npx vsce ls > dist/vsix-files.txt` 再 grep。但 `dist/` 在白名单里 → 下一次打包时这个清单文件自己被打了进去。

> **教训**：验证工具本身也要被验证。**负向测试**（故意放一个 `leak_probe.txt` 看门禁会不会拦）是唯一能证明门禁有效的方法。

### 结论与动作

| # | 动作 | 依据 |
|---|---|---|
| 1 | `vitest.config.ts` → `vitest.config.mts`，删除 `diff.expand` | 问题 1 二分定位 |
| 2 | `.vscodeignore` 增加 `.workbuddy/**` | 问题 2 根因 |
| 3 | `verify.sh` 第 5 段增加**打包内容白名单**断言，且改用**管道**不落中间文件 | 问题 2/3 |
| 4 | 白名单按 **fail-closed** 设计：新增要打包的目录必须显式加进白名单 | 黑名单永远会漏（问题 2 就是漏了） |
