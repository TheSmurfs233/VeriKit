## 2026-11-08 · S0 执行完成：骨架 + 五段门禁全绿（build 1）

### 背景

按 `docs/40_方案_S0_工程骨架.md` 执行 S0。本阶段目标只有一个：**建立"改坏了能立刻知道"的能力**，不写任何功能代码。

### 现象 / 问题

执行过程中撞到三个问题，按发现顺序：

1. `vitest run` 启动即崩，栈指向 `pathe` 的 `normalizeWindowsPath`。
2. **首次打包把 `.workbuddy/memory/2026-11-08.md` 打进了 vsix。**
3. 为防问题 2 复发而加的白名单检查，**自己的中间文件又被打进了包**。

```
首次打包的文件清单：
   LICENSE.txt / package.json / readme.md
   dist/extension.js
   .workbuddy/memory/2026-11-08.md     ← 不该出现
```

### 分析

**问题 1（vitest 崩溃）**：报错栈指向 `pathe` 的路径归一化，看起来像 vitest 内部 bug。
用二分法：删掉整份 `vitest.config.ts` 后能跑 → 逐项加回 → 定位到 `test.diff = { expand: true }` 这一行。
同时 `.ts` 配置在没有 `"type": "module"` 的包里按 CJS 加载，会打印 Vite 的 CJS 弃用警告 —— 改名为 `.mts` 后一并消失。

> **教训**：栈指向哪里不等于根因在哪里。栈说的是"崩在字符串处理"，根因是"配置对象里的一个字段让某个路径参数变成了 undefined"。**顺着栈查库源码会走偏，二分才有效。**

**问题 2（vsix 泄漏）**：`vsce package` 打印了包含文件清单，读了一下才发现多了一项。
如果只看最后一行的 `DONE Packaged` 就提交，一份含个人项目记忆的文件就随安装包分发出去了。
根因：`.vscodeignore` 只写了常规排除项（`src/`、`test/`、`docs/`、`node_modules/`），**漏了工具目录 `.workbuddy/`**。

> **教训：打包成功 ≠ 打包正确。** 判据必须是"打进去了哪些文件"，而不是"打包命令有没有报错"。
> 这正是 `07` 里"不要用被验证对象验证它自己"的一个实例 —— `vsce` 的退出码不能证明内容正确。

**问题 3（检查脚本污染打包）**：为了把问题 2 变成断言，加了白名单检查，实现是
`npx vsce ls > dist/vsix-files.txt` 再 grep。但 `dist/` 在白名单里 → 下一次打包时这个清单文件自己被打了进去。

> **教训**：验证工具本身也要被验证。**负向测试**（故意放一个 `leak_probe.txt` 看门禁会不会拦）是唯一能证明门禁有效的方法。

### 结论与动作

| # | 动作 | 依据 |
|---|---|---|
| 1 | `vitest.config.ts` → `vitest.config.mts`，删除 `diff.expand` | 问题 1 二分定位 |
| 2 | `.vscodeignore` 增加 `.workbuddy/**` | 问题 2 根因 |
| 3 | `verify.sh` 第 5 段增加**打包内容白名单**断言，且改用**管道**不落中间文件 | 问题 2/3 |
| 4 | 白名单按 **fail-closed** 设计：新增要打包的目录必须显式加进白名单 | 黑名单永远会漏（问题 2 就是漏了） |
| 5 | 补充 `LICENSE`（专有声明），消除 vsce 的 LICENSE 警告 | 减少"绿了但一堆噪音"的情况 |

## 2026-11-08 · 项目启动：流程规范改造 + 技术路线定案 + S0 方案

### 背景

要做一个 VSCode 的 Verilog 编辑辅助插件（轻量、跨平台、仅自用）。
项目起步时只有一份从 STM32 固件项目提炼的 `workflow/` 开发流程规范，没有任何代码。

### 现象 / 问题

1. 流程规范是嵌入式专用的：04 章讲"仿真先行"、06 章讲"硬件与安全"、07 章的 8 个案例全是电机/编码器。直接套到插件项目上会有 5 处水土不服。
2. 需求（8 条）看起来很多，但不确定哪些是"真开发"、哪些是"配置工作"。
3. 不确定该不该上 LSP。

### 数据

| 项 | 值 | 来源 |
|---|---|---|
| workflow 文件数 | 15（9 章 + 6 模板） | `ls workflow/` |
| 改造后需重写的章 | 3（04/06/07） | 逐章比对领域绑定内容 |
| 8 个需求 → 真正自研的块 | **1 块**（模块头解析） | 需求→能力归类（见 `10` 第 0 节） |
| 竞品自研解析器情况 | mshr-h: 无；TerosHDL: 部分；Digital IDE: Rust 重写 | 三者仓库 README |

### 分析

- **假设 A：功能多 → 工作量大。** 数据不支持：8 个需求里 7 个是外借（grammar / CLI / snippets），只有"模块树 + 例化 + 端口提示 + 模块名补全"共享一个内核，即模块头解析。
- **假设 B：要做得好就得自己写 parser + LSP。** 数据不支持：最流行的 mshr-h 完全没有自研解析器；而 Digital IDE 用 Rust + LSP 重写了 parser，版本仍在 0.5.0。
- **关键情报**：mshr-h 在 v1.26~v1.28 做过"工程模型 + 语义索引 + 层级树 + HDL Explorer + 托管 slang-server"，在 v1.29 全部撤回，原话是 "Restores the **stable** extension to the classic v1.25 architecture"。**这说明重架构的维护成本超过了收益。**
- **副作用发现**：mshr-h 的 README 里已经写明了我们预测到的两个坑 —— xvlog 要用临时目录做 cwd，以及 Windows 上要解析 `.exe`/`.cmd`/`.bat` 三种后缀。**说明这两条判断是对的，不用再自己踩。**

### 结论与动作

1. **把 `workflow/` 从嵌入式版改造为软件工程版**：重写 04（测试先行，四级金字塔）、06（外部依赖与安全）、07（换插件域案例）；改写 README/01/02/03/05/08 与 6 个模板。改完 15 份文件，文件名也改了（`04_测试先行.md`、`06_外部依赖与安全.md`）。
2. **技术路线定案**：只自研模块头解析，其余全部外借；不上 LSP；运行时零依赖。
3. **发现需求 2 的隐性依赖**：单文件 xvlog 检查会把跨文件例化报成 `VRFC 10-2063`，所以"语法检查"实际需要 filelist 概念，或至少需要按错误码过滤误报。已写入 `90` 与 `18`。
4. **放宽常驻进程约束**：从"0 常驻进程"改为"默认不启用 + 五条规则 + 可验收指标"，判据是 1000 文件全量索引 > 1 s。已写入 `workflow/06` 第 7 节。
