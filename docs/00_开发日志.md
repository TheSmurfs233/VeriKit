## 2026-11-09 · 信号聚焦：模块树内的信号流向标注（v0.13.0 build 39）

### 需求（用户设计，讨论两轮后拍板）

用户否决了"独立信号流视图"（怕与模块树脱节），提出**树上聚焦**交互：
例化节点右侧展开信号 → 点击某条信号 → 其他模块名后面出现箭头（类似端口的 inlay）→
扫一眼即知信号流向。**按需渲染，不常驻，无节点爆炸**——比独立视图更简，采纳。

### 实现

| 文件 | 层 | 内容 |
|---|---|---|
| `core/parse/instance.ts` | core | **`InstanceConnection` 补 `signal` 字段**（括号内表达式原样保留：普通/拼接 `{x,y}`；空串=悬空）——聚焦与悬空检测的数据地基 |
| `core/parse/indexer.ts` | core | `IndexedChild` 补 `connections`（端口→信号表），例化归属时随children入库 |
| `core/parse/hierarchy.ts` | core | `HierarchyNode` 补 `connections`，建树时从 child 条目透传 |
| `vscode/moduleTree.ts` | vscode | ① 常规态：例化节点 description = 端口统计（输入/输出/双向/**悬空**，按子模块端口方向归类）② 悬停行内按钮「信号」→ 展开**连接表**（`.clk → clk` / `.sum → （悬空）⚠`）③ 点击连接行 → **聚焦模式**：受影响例化节点 description 变 `→ 端口名（方向）`，根节点显示"聚焦: 信号名" ④ 命令面板「聚焦信号」QuickPick（全工程信号模糊搜索 + 取消聚焦）⑤ 同信号再点=取消 |
| `package.json` | 清单 | 2 个新命令（toggleSignalList 行内按钮 / focusSignal）+ inline 菜单；**命令总数 14** |

## 2026-11-09 · S4 第二批落地：onEdit 编辑时检查（可选配置，v0.10.0 build 32）

### 需求（用户拍板）

按讲解的方案实现 onEdit 可选配置：编辑时不保存也出红线（停止输入 1 秒后）。
方案确认三点：防抖 1s 固定、默认关、现在做。S4 至此完整收官。

### 实现

| 文件 | 层 | 内容 |
|---|---|---|
| `core/lint/bufferCopy.ts`（新增） | core | 缓冲副本写入器：`writeBufferCopy(fileName, text)` —— 临时目录独立、**保留原文件名与 .v 扩展**（xvlog 对两者敏感）、`dispose` 即删 |
| `core/trigger/policy.ts`（扩展） | core | `resolveChangeAction(onEdit, hasContentChanges)` 三态决策：磁盘回读→disk、用户输入+onEdit→buffer、否则 none |
| `core/trigger/debounce.ts`（新增） | core | `Debouncer`：连续 schedule 只保留最后一次、cancel、pending；schedule(fn) 支持按次传回调 |
| `vscode/lintScheduler.ts`（扩展） | vscode | `lint(doc, source: 'disk' \| 'buffer')`：buffer 模式先写副本再编译副本，诊断仍归原文档 URI，`finally` 清理；change 事件接 resolveChangeAction；save/close 取消挂起防抖；dispose 清全部 |
| `package.json` | 清单 | 配置声明 `verikit.check.onEdit`（boolean，默认 false，带代价说明） |

### 关键设计

| 点 | 说明 |
|---|---|
| 副本保留原文件名 | xvlog 对扩展名敏感，诊断消息文件名也来自它 |

## 2026-11-09 · 修 bug：索引重复收录导致模块树全部 ⚠ 且实例翻倍（v0.9.1 build 31）

### 现象（用户实测发现，附截图）

模块树里 `top` 和 `counter` 全部标"⚠ 多处定义"，`top` 下出现 **4 个**子实例
（u_counter_a / u_counter_b 各两个）—— 实际只有两个。

### 根因

索引重建时每个文件被处理了**两次**：磁盘扫描（`findFiles`）一次、"打开的文档"合并一次。
第二次时：
1. 模块定义因 `map.has` 被判成"多处定义"——**同一个文件和自己冲突** → 全部 ⚠
2. 但**例化挂接的代码没有跟着跳过** → `top` 的两个实例被挂第二遍 → 翻倍

`counter` 的 ⚠ 同理；`top` 的 ⚠ 也是（自己与自己冲突）。

### 修法（结构性，不是打补丁）

把索引重建抽成**纯函数** `core/parse/indexer.ts` 的 `rebuildIndex(files)`：
- **按文件去重**（后出现的覆盖前者：打开的文档覆盖磁盘版本）—— 从结构上杜绝重复调用的影响
- 冲突只统计**不同文件**（`list.includes(file)` 防御，同一文件不算冲突）
- `ModuleIndex.rebuild` 变薄：合并磁盘文件与打开文档（**开着的跳过磁盘扫描**）→ 调纯函数

### 回归测试（新增 5 条，第一条就是这个 bug）

| 用例 | 断言 |
|---|---|
| **同一文件传入两次** | 无冲突、children 不翻倍（本 bug 的最小复现） |
| 同文件重复传入、内容不同 | 后者覆盖（打开文档覆盖磁盘版本） |
| 同名模块在**不同文件** | 冲突 + ⚠（真正的冲突场景仍工作） |
| 例化归属 | top.children=2、counter.children=0 |
| 打开文档覆盖后 | 例化按新文本归属 |

## 2026-11-08 · 例化着色：模块名深蓝 / 实例名青 / .端口名浅棕（v0.5.2 build 22）

### 需求（用户指令）

例化语句着色三件套：例化的模块名 `counter` → **深蓝**；实例名 `u_counter_a` → **青**；
连接的端口名 `.ovf`（括号外）→ **浅棕**。

### 实现（TextMate 的硬限制与绕法）

初版用一条跨行正则匹配 `模块名 #(...) 实例名 (`，**JS 里测试通过、TextMate 里却完全不生效**。
根因：**TextMate 的 `match` 规则不能跨行** —— `tokenizeLine` 逐行喂文本，正则看不见换行符之外的世界。
而例化的参数表正好跨行。

绕法：拆成三条**行局部**规则，各管一种行形态：

| 规则 | 匹配 | scope |
|---|---|---|
| `instance-param` | `标识符` 后跟 `#(`（同行） | `entity.name.type.instance`（深蓝） |
| `instance-inline` | `标识符 标识符` 后跟 `(`（同一行，如 `adder u1 (`） | g1 深蓝 + g2 `entity.name.instance`（青） |
| `instance-name` | `)` 之后的标识符后跟 `(`（参数表跨行时，实例名独占一行） | `entity.name.instance`（青） |
| `port-connection` | `.端口名` 后跟 `(` | `variable.other.port`（浅棕 `#A0522D`） |

两个关键细节：
1. `instance-name` 需要 **lookbehind `)` + 关键字黑名单** —— 否则 `(posedge clk) begin` 的 `begin`
   会被误着成实例名。黑名单用负向前瞻 `(?!begin|end|if|...)\b`。
2. 模块名与实例名之间用 **`\s+` 强制要求空白**：初版用 `\s*` 时，正则引擎回溯会把
   `u_counter_a` 从下划线处拆成 `u_counter_` + `a` 来凑匹配（实测踩到）。`\s+` 让回溯路径失效。

手写 tmgrammar 断言的列号已经错了三次。这次写了自动对齐工具：

## 2026-11-08 · 修 bug：端口表行尾注释吞掉最后一个端口（v0.5.1 build 21）

### 现象（用户实测发现）

`top.v`（例化两份 counter）里，`.cnt` 有 input 虚影，但 **`.ovf` 没有** —— 两个实例的最后一项都缺失。

### 根因

`counter.v` 的端口表带行尾注释：

```verilog
    output reg [WIDTH-1:0] cnt,         // 当前计数值
    output                 ovf          // 溢出脉冲
```

端口表按逗号切分后，**上一行的行尾注释被拼进下一项的开头**：

```
项(cnt):  "output reg [WIDTH-1:0] cnt"                 ← 正常
项(ovf):  "        // 当前计数值\n    output  ovf  // 溢出脉冲"
```

解析"最后一个标识符"当端口名 → `ovf` 项的最后一个词是中文注释 `溢出脉冲`，
不匹配标识符正则 → **端口被静默丢弃**。

`cnt` 能显示纯属侥幸：它的注释（来自上一行 `en` 的行尾）在项的**开头**，端口名仍在末尾。

### 修法

新增 `blankComments(text)`：把注释内容**替换成等长空格**（保留换行与总长度），
端口表与连接表解析前先过一遍。

**为什么是等长替换而不是删除**：连接项的插入点依赖绝对下标（`findClose` 在原文上找配对括号），
等长替换保证所有下标不变 —— 这是硬约束，不是风格选择。

### 过程中的插曲（流程有效性的证明）

修完 `blankComments` 后我以为完事了，但**回归测试立刻失败** ——
因为我的替换脚本瞄准的旧代码行在上轮重构时已经变了，`replace` 静默没生效，调用点根本没接入。

**这正是回归测试的价值**：它抓住的不是"解析器有 bug"，而是"修复没真正落地"。
如果当时只跑 `verify.sh` 前没写这条测试，这个 bug 会以"修好了"的状态上线。

## 2026-11-08 · begin/end 分层变色 + 赋值符号默认黑（v0.3.2 build 15）

### 需求（用户指令）

1. `always` 块里可能有多对 `begin...end`，要求**每一对用不同颜色**（参考 TerosHDL）
2. 赋值符号 `<=` 与 `=` 不要蓝色，用默认黑

### 实现 1：begin/end 定深嵌套链

TextMate 没有语法树，做不到"自动数层数"。标准解法是**定深链**：

```
#block-1: begin=begin, end=end, 内容含 #statement 与 #block-2
#block-2: …内容含 #block-3
…
#block-6: 自递归（内容含 #statement 与 #block-6）
```

- 每层的 `begin`/`end` 给独立 scope：`keyword.other.block.l1..l6.verilog`
- 第 6 层自递归 → 深度超过 6 的嵌套保持第 6 层颜色，**不会漏匹配也不会错位**
- `case...endcase`、`module...endmodule` 不计入层级（用户只要求 begin/end）

**实测**（`test/grammar/dump.js` 对嵌套样例分词）：

```
1 |     always @(posedge clk) begin
     26-31 "begin"  keyword.other.block.l1.verilog
2 |         if (en) begin
     16-21 "begin"  keyword.other.block.l2.verilog
4 |             if (full) begin
     22-27 "begin"  keyword.other.block.l3.verilog
5 |             end
     12-15 "end"    keyword.other.block.l3.verilog
6 |         end
      8-11 "end"    keyword.other.block.l2.verilog
7 |     end
      4- 7 "end"    keyword.other.block.l1.verilog
```

配色（浅色主题）：L1 蓝 `#0000FF`、L2 橙 `#B45F04`、L3 青 `#0E8A8A`、L4 紫 `#AF00DB`、L5 红 `#A31515`、L6 橄榄 `#6B8E23`。要换色板改 6 行即可。

### 实现 2：`<=` 与 `=` 默认黑

- 新增 `#assignment` 规则：`match: "<=|=(?![=])"`，scope 名 `assignment.operator.verilog`
- **放在 `#operator` 之前**；`= ` 用负向前瞻 `(?![=])`，否则会吞掉 `==` / `===` 的第一个等号
- `#operator` 的字符类里删掉了 `=`，并把 `<=` 从多字符分支里移除
- **给了 scope 名但没有任何颜色规则** → 主题查不到 → 渲染为默认黑色；同时测试里可以断言它

### 过程中的两次自我踩坑（都值得记）

1. **手工数空格对不齐断言列**。`vscode-tmgrammar-test` 的标记行靠列对齐，我连错了三次。
   正确做法：先用 `test/grammar/dump.js` 量出每个 token 的真实列号，再用脚本按列号**生成**标记行，
   而不是人肉数空格。
2. **用脚本改标记行时把代码行覆盖了**。脚本的条件写漏了索引限制，把 `    q <= ~q;` 这行代码
   替换成了标记行。教训：**按索引写文件之前，先打印改前/改后的两行确认**。

## 2026-11-08 · 修片段 `$` 转义 + 定位"改完仍全蓝"的真因（v0.2.2 build 11）

### 背景

F5 后出现两条反馈：

1. 右下角弹提示：「扩展"verikit"中的一个或多个代码片段很可能混淆了片段变量和片段占位符」
2. 高亮**仍然是清一色的蓝**，拆分 scope 之后没变化

### 问题 1：`$finish` 被当成片段变量

**数据**：`snippets/verilog.json` 里 `"        #1000 $finish;"`
（`$0` 是合法的最终制表位，不受影响）。

**根因**：VS Code 片段语法里 `$name` 是**变量引用**，`${n:默认值}` 是**占位符**。
`$finish` 被解析成"未知变量"，于是弹那条提示。正确写法是 `\$finish`。

**修法**：
| # | 动作 |
|---|---|

## 2026-11-08 · 高亮配色太单调：拆 scope（v0.2.1 build 10）

### 背景

S2 上线后用户反馈：**"颜色太单调"**，并给了两张参考图。

### 现象 / 问题

自己的截图里，`module` / `input` / `output` / `reg` / `always` / `begin` / `if` / `else` / `endmodule`
**全是同一种蓝色**，只有注释（绿）和数字（青）是别的颜色。

### 分析

根因不在 grammar 的覆盖度，而在 **scope 粒度**：

> 改之前我把所有关键字塞进了同一个 `keyword.control.verilog`。
> TextMate 的着色流程是 `正则 → scope 名 → 主题按 scope 上色`，
> **同一个 scope 必然是同一种颜色** —— 覆盖再全也只有一种颜色。

参考图里至少分了四类：控制关键字（紫）/ 块与类型（蓝）/ 模块名（青）/ 注释（绿）。
也就是说它对同一个词给了不同 scope。

顺带发现两个覆盖缺口：
- `or`（敏感列表里的连接词）**完全没匹配**，落成普通标识符
- `posedge` / `negedge` 用的是 `keyword.operator.edge`，很多主题不给它单独上色

### 结论与动作

把关键字按语义拆成 4 类（都选主题普遍支持的标准 scope）：

| scope | 内容 | 典型配色（Light+ / Dark+） |
|---|---|---|
| `keyword.control.verilog` | always / initial / if / else / case / for / while / assign / generate / wait | 紫 |
| `keyword.other.block.verilog` | begin / end | 蓝 |
| `keyword.other.edge.verilog` | posedge / negedge / edge / **or** | 蓝 |
| `keyword.other.module.verilog` | module / endmodule / primitive | 蓝 |
| `storage.type.verilog` | input / output / inout / reg / wire / logic / integer | 蓝 |
| `storage.modifier.verilog` | parameter / localparam / defparam / genvar / signed | 蓝 |
| `entity.name.type.module.verilog` | 模块名 | 青 |
| `entity.name.function.verilog` | task / function 名（新增） | 青 |

同时新增 `#task-function` 规则：`task automatic do_calc(...)` 里
`task` 归 `keyword.control.task`、`do_calc` 归 `entity.name.function`。

**为什么要用标准 scope 而不是自定义名字**：主题是按 scope 的**最长已知前缀**匹配的。
`keyword.other.block.verilog` 会先找自己，再退到 `keyword.other`，再退到 `keyword`；
随便起个 `verilog.block.marker` 则谁都匹配不上，等于没上色。

### 验证

| 项 | 结果 |
|---|---|
| grammar 测试 | 12 组断言通过（新增 begin / posedge / or / end 四处） |
| 列对齐 | `begin` 在第 43 列，断言一次通过 |
| `verify.sh` 六段 | ✅ ALL GREEN |

### 遗留

- [ ] 手验：是否真的分出 3~4 种颜色，以及哪个词的色还不符合预期
- [ ] 若某个词要特定颜色，调它的 scope 即可（`syntaxes/verilog.tmLanguage.json` 里改一行 + 改一条断言）

- 报错路径里的 `ssr\<hash>` 是 **Vite 的 SSR 转换缓存**，落在系统临时目录；同一 hash 每次相同，父目录随机 → 是"同一份缓存被并发写"。

## 2026-11-08 · 实测推翻"xvlog 单文件必然误报"的判断，并摸清诊断格式

## 2026-11-08 · 修 `.bat` 启动形态：版本查询 53 ms 失败（v0.1.1 build 6）

### 背景

S1 手动验收时，状态栏能显示 `xvlog`，但**没有版本号**。日志里这一行不对：

```
[probe] presence: found via path  D:\Xilinx\Vivado\2022.2\bin\xvlog.bat  (4 ms)
[probe] version: 未知  (53 ms)
```

53 ms 不可能跑完 `xvlog`（此前实测约 1000 ms），说明进程几乎立刻退出了。

### 现象 / 问题

- 存在性探测正常（4 ms，走 PATH 命中）—— 顺带推翻了我之前"PATH 里没有 Vivado"的判断
- 版本查询失败，且日志里**没有原始输出**，只能去外部复现

### 数据

写了个临时脚本对比三种启动形态（目标 `xvlog.bat`，cwd 为临时目录）：

| 形态 | 结果 |
|---|---|
| A `cmd /d /s /c "path -version"`（原实现） | ❌ code=1, **50 ms**；stderr 是"`'\"D:\...\xvlog.bat -version\"'` 不是内部或外部命令" |
| B `cmd /d /s /c call path -version` | ✅ code=0, 1257 ms, `Vivado Simulator v2022.2` |
| C 直接 spawn `.bat` | ❌ `EINVAL` |

补充验证 B 在**路径含空格**时仍然正确：造了 `...\Program Files X\fake tool.bat`，
`call` 形态返回 `FAKE-OK hello`，code=0。

### 分析

- 根因是 **Node 的 argv 转义**：`spawn('cmd.exe', ['/d','/s','/c','"C:\\path\\x.bat -version"'])`
  里那个带引号的参数含有空格和引号，Node 会把它转义成 `\"...\"` 再拼到命令行上。
  cmd 收到的是**字面量反斜杠+引号**，于是把整串当成一个不存在的命令名。
- 我之前的设计假设是"手工拼一条 `/s /c "..."` 就能控制引号形态"——**这个假设错了**，
  而且纯函数单测测不出来：单测只验证我拼出来的字符串长什么样，验证不了 Node 最终交给系统的是什么。
- 正解是**不拼命令行**：把 `call` 作为 cmd 的命令、路径与参数各自作为独立 argv 交出去，
  加引号的活交给 Node 做（它对每个参数单独处理，含空格才加引号）。
- 另一处缺陷：**日志里没有原始输出**。53 ms 失败时，stdout/stderr 全是空的还是报错文本，
  日志没记，只能另写脚本复现。观测性不足导致多花了一轮。

### 结论与动作

| # | 动作 |
|---|---|
| 1 | `buildSpawnPlan` 改为 `['/d','/s','/c','call', target, ...args]`，不再手工拼引号 |
| 2 | 保留元字符校验（`& \| < > ^ "` 一律拒绝），因为我们确实要经过 cmd |
| 3 | **新增真实进程回归测试** `test/unit/winShim.spawn.test.ts`：造一个"目录名+文件名都带空格"的 `.bat`，用 `runCapture` 真跑一遍；再验非零退出码。平台门控 `describe.skipIf(!isWindows)` |
| 4 | `toolchainService` 在拿不到版本时**打印原始 code/stdout/stderr（截断 300 字）** —— 下次不用再写外部脚本 |
| 5 | 版本 `0.1.0 build 5` → **`0.1.1 build 6`** |

### 验证

| 项 | 结果 |
|---|---|
| `tsc --noEmit` | 0 error |
| `vitest` | **39 passed / 7 files**（新增的 `.bat` 真实进程用例包含在内） |

### 分析

**问题 1（vitest 崩溃）**：报错栈指向 `pathe` 的路径归一化，看起来像 vitest 内部 bug。
用二分法：删掉整份 `vitest.config.ts` 后能跑 → 逐项加回 → 定位到 `test.diff = { expand: true }` 这一行。
同时 `.ts` 配置在没有 `"type": "module"` 的包里按 CJS 加载，会打印 Vite 的 CJS 弃用警告 —— 改名为 `.mts` 后一并消失。

> **教训**：栈指向哪里不等于根因在哪里。栈说的是"崩在字符串处理"，根因是"配置对象里的一个字段让某个路径参数变成了 undefined"。**顺着栈查库源码会走偏，二分才有效。**

**问题 2（vsix 泄漏）**：`vsce package` 打印了包含文件清单，读了一下才发现多了一项。
如果只看最后一行的 `DONE Packaged` 就提交，一份含个人项目记忆的文件就随安装包分发出去了。
根因：`.vscodeignore` 只写了常规排除项（`src/`、`test/`、`docs/`、`node_modules/`），**漏了工具目录 `.workbuddy/`**。

> **教训：打包成功 ≠ 打包正确。** 判据必须是"打进去了哪些文件"，而不是"打包命令有没有报错"。
> 这正是 `07` 里"不要用被验证对象验证它自己"的一个实例 —— `vsce` 的退出码不能证明内容正确。

**问题 3（检查脚本污染打包）**：为了把问题 2 变成断言，加了白名单检查，实现是
`npx vsce ls > dist/vsix-files.txt` 再 grep。但 `dist/` 在白名单里 → 下一次打包时这个清单文件自己被打了进去。

> **教训**：验证工具本身也要被验证。**负向测试**（故意放一个 `leak_probe.txt` 看门禁会不会拦）是唯一能证明门禁有效的方法。
