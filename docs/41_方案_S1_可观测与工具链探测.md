# S1 可观测与工具链探测 方案

> 日期：2026-11-08 · 状态：**已完成并通过手动验收（v0.1.1 build 6）** · 实际工期：约 1.5 小时

---

## 1. 背景

S0 建立了门禁，但插件现在只会打印自己的版本 —— **它不知道 `xvlog` 在哪、能不能跑、跑一次多慢**。

这三件事必须在写任何功能之前搞清楚，因为：

1. **S4 的诊断功能整体依赖探测结果**：探不到工具链，诊断就是空的
2. **触发策略的参数取决于冷启动耗时**：如果一次 `xvlog` 要 2 秒，"编辑时触发"这个选项就根本不该存在
3. **现在没有可靠的观测手段**。`07_调试方法论` 的核心教训是"先测量再修改"，而目前唯一的仪表是一个打印环境信息的命令

## 2. 目标（可验证）

| # | 目标 | 验收标准 | 级别 | 测法 |
|---|---|---|---|---|
| 1 | 能探测到 `xvlog` 并拿到绝对路径 | 三级级联（配置 → PATH → 候选目录）任一命中即成功；命中来源要能说清 | L1 + L4 | 单测 fixture + 命令 |
| 2 | 探测失败有明确降级 | 四类异常（未安装 / 路径配错 / 不是文件 / 无执行权限）各有可读提示，**不抛未捕获异常** | L1 + L4 | 单测 + 手动 |
| 3 | **实测 `xvlog` 冷启动耗时** | 记录三组数据：首次 / 后续 / 含 include 的文件；写进 `00_开发日志` | L4 | 手动 + 导出 JSON |
| 4 | `VeriKit: 导出诊断 JSON` 可用 | 输出结构化 JSON，含 `env` / `toolchain` / `probe.phases`；字段齐备 | L1 + L3 | 单测 schema + 命令 |
| 5 | 状态栏能反映工具链状态 | 显示 `xvlog 2022.2` 或 `工具链未找到`；点击可看详情 | L4 | 手动 |
| 6 | **激活不受探测影响** | 激活日志第 1、2 行的时间差 < 50 ms（证明探测没在激活体里跑） | L1 | 日志打时间戳 |

> 然后每个 VSCode 窗口都多背几百毫秒 —— 而这种退化在开发机上几乎感觉不到。

## 4. 技术路线

### 4.1 探测策略选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 只读用户配置的绝对路径 | 零误判、实现最简单 | 首次使用体验差（必须先手填） | ❌ 不单独使用 |
| B. 配置 → PATH 查找 | 覆盖"终端里能用"的多数情况 | 从桌面图标启动的 VSCode，PATH 可能不含 Vivado | ✅ 主路径 |
| **C. B 失败后扫描候选安装目录** | 覆盖"装了但没进 PATH"（Vivado 的典型情况） | 平台相关、可能慢 | ✅ **作为兜底，只在 B 失败时执行一次** |

**结论：三级级联 `配置 → PATH → 候选目录`，结果缓存。**

### 4.2 关键设计

```ts
// core/toolchain/types.ts
export type ProbeSource = 'config' | 'path' | 'scan' | 'none';

export interface ProbeAttempt {
  via: string;          // 'config' | 'PATH' | 'XILINX_VIVADO' | 'D:/Xilinx/Vivado/*/bin'
  target: string;       // 试过的具体值（路径或环境变量名）
  result: 'ok' | 'missing' | 'notExecutable' | 'notFile';
}

export interface ProbeResult {
  found: boolean;
  exePath?: string;     // 命中的绝对路径
  version?: string;     // 拿不到时为 undefined，不阻塞
  source: ProbeSource;
  attempts: ProbeAttempt[];   // ★ 失败时能说清"我试过哪些路"
  elapsedMs: number;
}
```

`attempts[]` 是这个设计里最重要的字段。工具链探测失败时，用户最想知道的是**"你找过哪里"**，
而不是一句"未找到"。这条信息也让 `导出诊断 JSON` 有实际价值。

```ts
// core/toolchain/detect.ts —— 纯函数，不 import vscode，fs 可注入
export async function detectXvlog(opts: {
  configuredPath: string;
  env: Record<string, string | undefined>;
  platform: NodeJS.Platform;
  exists: (p: string) => Promise<boolean>;   // 注入点，便于单测三平台
}): Promise<ProbeResult>;
```

**Windows 上的关键细节**：`xvlog` 有三个可能的载体 `xvlog.exe` / `xvlog.cmd` / `xvlog.bat`。
本机实测只有 `.bat`。存在性检查必须按顺序试这三个后缀 —— 这也是 `06` 章已记录的坑。

### 4.3 ProcessRunner（最小版）

S1 只需要一个能力：**跑一条命令、收全 stdout/stderr、带超时、返回退出码**。

```ts
// core/proc/runner.ts
export interface RunResult {
  code: number | null;
  stdout: string;
  stderr: string;
  elapsedMs: number;
  timedOut: boolean;
}
export async function runCapture(cmd: string, args: string[], opts: {
  cwd: string; timeoutMs: number; signal?: AbortSignal; encoding?: string;
}): Promise<RunResult>;
```

S1 必须做对的三件事（都是 `06` §3.3 里记过的坑）：

| 要点 | 做法 |
|---|---|
| 同时消费 stdout / stderr | 两路都监听 `data`，**否则管道写满会永久挂起** |
| 用 `close` 而不是 `exit` 判断结束 | `exit` 早于输出读完，会截断 |
| 超时即 kill | 超时后 `kill()` 并标记 `timedOut`，不抛异常 |

取消（`AbortSignal`）在 S1 只是留接口，S4 才真正用上。

### 4.4 外部依赖

| 依赖 | 是否必须 | 缺失时的行为 |
|---|---|---|
| `xvlog`（Vivado 2022.2） | 否 | **不崩溃、不弹窗**；状态栏显示"工具链未找到"；`导出诊断 JSON` 里 `attempts[]` 列出所有试过的路径 |

### 4.5 配置项设计

| 配置键 | 类型 | 默认 | scope | 说明 |
|---|---|---|---|---|
| `verikit.toolchain` | enum `xvlog` \| `none` | `xvlog` | resource | 选哪个工具；可按工程覆盖 |
| `verikit.xvlog.path` | string | `""` | **machine** | 绝对路径；空则走三级级联探测 |
| `verikit.probe.scanDirs` | string[] | `[]` | **machine** | 兜底扫描目录，不硬编码任何厂商路径 |
| `verikit.check.timeout` | number(ms) | `10000` | resource | 单次外部进程超时 |

三条设计决定（都有代价，写清楚原因）：

1. **每工具一个独立键**（`verikit.xvlog.path`），不共用一个 `verikit.toolchain.path`。
   共用的话，切换工具时上一个工具的路径就丢了；S4 加 ModelSim 时还得再迁一次配置。
2. **路径类配置必须是 `machine` scope。** `resource`（默认值）允许写进 `.vscode/settings.json`，
   而那份文件会进 git —— 路径跟着仓库走，换台机器或别人克隆下来全是错的。`machine` 只能写用户级，从机制上堵死这条路。
3. **不提前声明 `verikit.modelsim.path` / `iverilog.path`。** 声明了用不上，用户配了没反应，
   会以为插件坏了。S4 扩 `enum` 并新增键，是向后兼容的。

配套提供命令 **`VeriKit: 选择工具链可执行文件`**：用系统文件对话框选，直接写用户级设置
（`ConfigurationTarget.Global`），避免用户手打路径 —— 手打最常见的错误是填到了 `bin` 目录而不是文件本身。

### 4.6 实测结果（2026-11-08，本机）

| 项 | 值 |
|---|---|
| `xvlog.bat -version` 输出 | `Vivado Simulator v2022.2` |
| 首次（磁盘冷）耗时 | **2016 ms** |
| 连续三次耗时 | 1002 / 977 / 1022 ms |
| 在 cwd 留下的文件 | `xvlog.log`、`xvlog.pb`（**只查版本也会产生**） |
| `XILINX_VIVADO` 环境变量 | 本机未设置 |

三条直接结论：

1. **版本查询也要背着临时目录跑。** 即使 `-version` 也会污染 cwd —— `06` 章那条"用临时目录做 cwd"不是只针对真正的编译。
2. **一次探测约 1 s。** 所以探测必须懒执行 + 缓存，绝不能放在 `activate()` 里，也不能每次刷新状态栏都重探。
3. **S4 的触发策略里，`onEdit`（编辑时防抖触发）应该彻底移除，而不是"默认关闭"。** 每次 1 s 起的外部进程 + 持续打字，
   只会让风扇一直转。留一个默认关闭的选项等于给未来的自己埋雷。

| 步 | 内容 | 产出 | 状态 |

| 3 | `core/toolchain/*`（adapter / pathLookup / detect / version）+ 单测 | 纯函数探测逻辑 | ✅ |
| 4 | `core/path/expand.ts` + 单测 | `${env:}` 与 `~` 展开 | ✅ |
| 5 | 配置项 + 选择文件命令 + 配置变更防抖重探 | 用户可自配路径 | ✅ |
| 6 | `vscode/toolchainService.ts` 状态栏 + 4 个命令 | 可见的降级出口 + 观测手段 | ✅ |

**步 1 必须先做**，因为它决定步 3 是否需要"跑子进程拿版本"这条分支 —— 本例里 `xvlog` 支持
`-version`，所以版本分支保留；但代价是每次探测多 1 s，于是"快速路径 / 慢速路径"必须分开（见 §4.6 结论 2）。

### 5.1 实施中与方案的偏差

| 项 | 方案 | 实际 | 原因 |
|---|---|---|---|
| 文件组织 | 一个 `toolchainStatus.ts` 管状态栏 | `ToolchainService` 同时管状态、缓存与状态栏 | 状态栏就是状态的投影，拆开反而要来回同步 |
| 探测返回值 | `ProbeResult` 单层 | `PresenceResult`（快，纯 fs）+ `VersionProbe`（慢，起进程）分离 | 实测版本查询 1 s，若与存在性检查合并返回，状态栏要白等 1 s |
| 新增单测文件 | 未列 | `winShim` / `pathLookup` / `expand` / `detect` / `runner` 共 5 个 | 把跨平台与引号问题做成纯函数，才可能在单测里覆盖 |

## 6. 验证方法

| 项 | 级别 | 方法 | 期望 |
|---|---|---|---|
| 探测三平台分支 | L1 | 注入伪 `platform` + 伪 `exists` | 6 条用例全过 |
| 四类异常 | L1 | fixture 覆盖 missing / notFile / notExecutable / 配置错 | 每种都有明确 `result` 且不抛异常 |
| 进程双流消费 | L1 | 起一个大量输出的子进程 | 不挂起、输出完整 |
| 超时 | L1 | 起一个 `sleep` 类子进程，timeout=200ms | `timedOut=true`，耗时 < 1s |
| 命令注册 | L3 | `@vscode/test-electron` | 两个命令都存在 |
| 激活不阻塞 | L1 | 日志时间戳差 | < 50 ms |
| 真实探测 | L4 | 手动执行命令 | 命中 `xvlog` 并显示版本（或明确未找到） |

### 6.1 不做自动化的部分及理由

| 项 | 理由 | 补偿措施 |
|---|---|---|
| 真实 `xvlog` 的输出格式 | 依赖本机 Vivado 版本，且拉起成本 1~3 s | 把真实输出**原样**存成 fixture，供 S4 复用 |
| 冷启动耗时 | 依赖机器负载，不可断言 | 只记录不设门槛；数据进 `00`，作为 S4 的参数依据 |
| 状态栏观感 | 渲染层 | 手动检查一次 |

### 6.2 会写用户文件的部分

**无。** 临时文件一律写 `os.tmpdir()`，进程结束即清理。

## 7. 风险与对策

| # | 风险 | 可能性 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | `xvlog` 不支持版本命令 | **高** | 拿不到版本，状态栏显示"未知" | 降级为存在性检查，不阻塞；版本留空 |
| 2 | 扫描候选目录很慢（`Xilinx` 目录树很深） | 中 | 首次探测卡住 | 只扫一层的 `*/bin/\*`，不递归；结果缓存到 `globalState` |
| 3 | 冷启动远超预期（> 3 s） | 中 | S4 的体验目标要下调 | 实测数据决定；若 > 2 s，则"编辑时触发"从配置里彻底移除 |
| 4 | 桌面启动的 VSCode PATH 不含 Vivado | **高** | 探测不到 | 三级级联 + `XILINX_VIVADO` 兜底 + 可手配路径 |
| 5 | 探测在激活体里跑（违反 §5.3） | 中 | 每个窗口慢几百 ms | 目标 6 用时间戳断言把它钉死 |

## 8. 回退方案

- S1 只新增文件 + 一个状态栏项 + 一个命令，**不修改任何既有行为**
- 一键关闭：`verikit.toolchain: "none"` → 探测完全不执行，状态栏显示"已禁用"
- 若 ProcessRunner 出问题，可先注释掉 `exportDiagnostics` 命令，其余功能不受影响
