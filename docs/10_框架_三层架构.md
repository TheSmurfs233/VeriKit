# 三层架构

> 代码位置：`src/`
> 本文回答两个问题：**为什么这样分层**、**为什么只有一块要自研**。

---

## 0. 路线声明（先看这一节）

> **除"模块头解析"之外，全部外借。**

| 需求 | 来源 | 自研量 |
|---|---|---|
| 代码高亮 | **自写 Verilog-2001 子集**（`syntaxes/verilog.tmLanguage.json`，约 90 行） | 小 |
| 代码片段 | 手写 snippets | 小 |
| 语法检查 | 外部 CLI（xvlog） | 适配层 |
| 代码格式化 | 外部 formatter（iStyle / verible） | 适配层 |
| **模块头解析** | **自研 `core/netlist/`** | **中** |
| 模块树 | 解析结果的 TreeView 渲染 | 小 |
| 一键例化 | 解析结果 + 模板 + `WorkspaceEdit` | 小 |
| 端口提示 | 解析结果的 HoverProvider | 小 |
| 模块名补全 | 解析结果 + CompletionItem | 小 |

**8 个需求 = 1 块内核 + 7 个薄封装。**

这个比例是刻意的：竞品分析表明，凡是把自研扩展到"完整 parser / 语义分析"的插件（Digital IDE、TerosHDL）复杂度都会跳一个台阶，而最流行的那个（mshr-h）恰恰是因为**不自研解析器**才轻。
详见 `00_开发日志` 2026-11-08 条目的竞品分析。

## 1. 职责

**负责**：
- 把 Verilog 源码文本解析成"模块 / 参数 / 端口"结构
- 调用本机工具链并把各家输出归一化成统一诊断
- 把上述结果渲染成编辑器的可视化能力

**不负责**：
- 不做语法正确的代码生成（例化只做模板填充，不保证语义正确）
- 不做编译 / 综合 / 仿真运行
- 不做跨工作区的依赖解析（`.xpr` / IP 库）

## 2. 分层与依赖方向

```
┌──────────────────────────────────────────────┐
│  表现层  src/vscode/                          │  ← 命令、DiagnosticCollection、TreeView、
│  可以 import vscode                           │     HoverProvider、状态栏
├──────────────────────────────────────────────┤
│  能力层  src/core/        ★ 禁止 import vscode │  ← 模块头解析、诊断归一化、索引、路径
│  纯 TypeScript，可在 vitest 中直接测试         │
├──────────────────────────────────────────────┤
│  进程层  src/core/proc/runner.ts              │  ← 全项目唯一 spawn 出口
└──────────────────────────────────────────────┘
                       ↓
             外部工具链（xvlog / formatter）
```

**依赖只能自上而下。** 反过来就是设计错误。

### 2.1 为什么"core 禁止 import vscode"是硬约束

```ts
// ❌ 这一行加上去，这个文件就永久失去单测能力
import * as vscode from 'vscode';
```

后果不是"少写一个测试"，而是：
- 它只能在扩展宿主里跑 → 只能手动验证 → 回归成本从 0.2 秒变成 50 秒
- 它无法参与 corpus 快照回归 → 模块头解析的错误变成静默错误

**执行方式**：`test/arch.js` 扫描 `src/core/**`，发现 `from 'vscode'` 即 FAIL，进 `verify.sh`。
这条约束**必须机械化**，靠人记住一定会退化。

## 3. 数据结构

```ts
// core/netlist/types.ts
export interface Port {
  name: string;
  direction: 'input' | 'output' | 'inout';
  widthText: string;        // 原样保留，如 "[WIDTH-1:0]"，不展开宏
  type?: string;            // reg / wire / logic，可缺省
  comment?: string;         // 端口前的注释，用于悬停提示
  line: number;             // 1-based
}

export interface ParamDecl {
  name: string;
  defaultValue: string;     // 原样保留文本
  line: number;
}

export interface ModuleDecl {
  name: string;
  file: string;
  line: number;
  params: ParamDecl[];
  ports: Port[];
  isAnsiPortList: boolean;  // false 时 ports 可能不完整，需在 UI 上提示
}
```

### 状态机（模块头解析器内部）

```
扫描态 ──"//"──→ 行注释态 ──换行──→ 扫描态
       ──"/*"──→ 块注释态 ──"*/"──→ 扫描态
       ──"\""──→ 字符串态  ──"\""──→ 扫描态
       ──"module"──→ 模块头态 ──";"──→ 扫描态（记录 ModuleDecl）
```

| 状态 | 含义 | 可接受的转移 |
|---|---|---|
| 扫描态 | 普通代码 | 进入注释/字符串/模块头 |
| 注释态 | `//` 或 `/* */` 内 | 只回到扫描态，**内容不入 token** |
| 字符串态 | `"..."` 内 | 只回到扫描态 |
| 模块头态 | `module` 到 `;` 之间 | 收集 params 与 ports |

> **注释态与字符串态是必须的**：否则 `// module foo` 这种注释会被当成真模块，`"module"` 字符串同理。

## 5. 算法 / 流程

### 5.1 语法检查链路

```
文档事件 → 触发策略（core/trigger/policy.ts）
        → 调度器（序号 +1，取消上一次）
        → ProcessRunner.spawn(xvlog, args)  ← 唯一出口
        → 原始 stderr → 诊断归一化（core/diag/normalize.ts）
        → 误报过滤（错误码白名单）
        → DiagnosticCollection 整簇替换
```

**单位约定**：行号 1-based（与 VSCode `Diagnostic` 一致）；列号在 xvlog 中不可得，统一填 0。

### 5.2 索引链路

```
文件扫描 → 模块头解析 → 索引 Map<moduleName, ModuleDecl[]>
        → TreeView 渲染 / 悬停查询 / 例化模板生成
```

### 5.3 激活与探测时机（S1 的实现约束）

`activationEvents` 是 `onStartupFinished`，意味着**每个窗口启动都会加载本插件**。因此：

| 约束 | 原因 |
|---|---|
| **激活体里不许跑工具链探测** | 探测要起子进程，会把每个窗口的启动拖慢几百毫秒到几秒 |
| 探测改为**懒执行**：首次需要时（点命令 / 打开 `.v` / 保存）才探测一次，结果缓存 | 没有 Verilog 文件的窗口完全零开销 |
| 激活体只做：创建 OutputChannel、注册命令、注册（不触发）监听 | 保证"日志首行有版本号"这条能成立，同时不产生副作用 |
| 探测失败**不弹窗**，只在状态栏留提示 | 队友/用户不该为插件环境问题被打断 |

> 这条约束是 S0 验收时暴露的：`onStartupFinished` 让"首行有版本号"成立，代价是插件必被加载。
> 那就更不能在激活路径上放任何 I/O。

## 7. 坑与注意事项

| # | 坑 | 现象 | 原因 | 规避 |
|---|---|---|---|---|
| 1 | Windows 上 `.bat` 不能直接 `spawn` | ENOENT，但命令行能跑 | libuv 不加 `.bat` 后缀 | 解析 `.exe`/`.cmd`/`.bat` 三种，`.bat` 走 `cmd /c` |
| 2 | xvlog 往 cwd 写文件 | 用户工程目录多出 `xsim.dir/`、`xvlog.log` | xvlog 默认输出到当前目录 | 以临时目录为 cwd 启动，源文件与 `-i` 路径全传绝对路径 |
| 3 | 注释里的 `module` 被当成模块 | 模块树出现不存在的模块 | 解析器没跳过注释态 | 状态机必须先处理注释/字符串 |
| 4 | 诊断只在保存后更新，编辑时不更新 | 用户以为坏了 | 触发策略默认不含 `change` | 配置项可开 `onEdit`；状态栏显示上次检查时间 |
| 5 | 快速编辑后诊断与代码对不上 | 旧结果覆盖新结果 | 无竞态保护 | 请求序号 + 过期丢弃 |
| 6 | **路径大小写/分隔符不一致导致诊断丢失** | 编辑器里该红的地方不红，且无任何报错 | VSCode 的 `document.fileName` 给 `d:\...`，而工具回显 `d:/...`（实测同一次检查两者并存） | 路径比较前统一 `toLowerCase()` + `replace(/\\/g,'/')`；**比较必须是"归一后相等"，不是字符串直接比** |
| 7 | 每次检查都重新探测工具链 | 一次检查白花约 1.6 s | `probe()` 无缓存判断 | 命中缓存直接返回；只有改配置/显式刷新才 `force` |
