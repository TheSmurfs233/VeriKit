# 配色参考（让高亮看起来像参考图）

> 背景：把关键字按语义拆成 8 类 scope 之后，用户在编辑器里看到的**仍然全是同一种蓝色**。
> 本文解释原因，并给一个确定性的解法。

---

## 0. 改颜色之前先确认：生效的是哪个 grammar

**换主题也不变色，说明可能根本不是主题的问题。**

宿主窗口（F5 打开的那个）默认会加载**所有已装扩展**。如果机器上装了
`mshr-h.veriloghdl`、`teros-technology.teroshdl`、`sterben.fpga-support` 之类的 HDL 插件，
它们**也会给 `verilog` 注册 grammar**，而 VSCode 对同语言的多个 grammar 只用一个 —— 谁最后注册谁生效。

于是会出现：改了本插件的 grammar，屏幕上却毫无变化。

### 三步确认

**① 直接查扩展**

```
Ctrl+Shift+P → "VeriKit: 诊断语言与着色"
```

Output 面板会列出所有给 `verilog` / `systemverilog` 提供语言或 grammar 的扩展，
以及当前 `languageId`、当前主题名。**如果列出两个以上，就说明着色可能不是本扩展的。**

**② 干净环境复验（最快）**

```
运行面板 → 选 "★ 运行扩展（干净环境，推荐）" → F5
```

这个启动配置带了 `--disable-extensions`，宿主只加载本扩展。此时看到的颜色一定是本插件的 grammar 产出的。
**如果颜色一下子分开了，就 100% 确认是扩展冲突。**

**③ 证明 grammar 本身没问题**

```bash
node test/grammar/dump.js ../test-workspace/rtl/broken.v 5 13
```

它用 `vscode-textmate` 对真实文件分词，打印每行的 token 与 scope。
本机实测输出（2026-11-08）：

```
 5 | module broken (
      0- 6  "module"   keyword.other.module.verilog
      7-13  "broken"   entity.name.type.module.verilog
11 |     always @(posedge clk or negedge rst_n) begin
      4-10  "always"   keyword.control.verilog
     13-20  "posedge"  keyword.other.edge.verilog
```

**四种不同 scope 正确产出** → grammar 没问题，问题一定在"VSCode 用了哪份 grammar"。

**④（可选）看单点的 scope**

```
把光标放在某个关键字上 → Ctrl+Shift+P → "Developer: Inspect Editor Tokens and Scopes"
```

弹窗里会显示该位置的 scope 栈。本插件的 `always` 应是 `keyword.control.verilog`；
如果是别的名字，说明用的不是我们的 grammar。

---

## 1. 为什么拆了 scope 还是全蓝（已用数据确认）

TextMate 的着色链条是三段：

```
正则匹配 → 产出 scope 名（如 keyword.control.verilog）→ 主题按 scope 查表决定颜色
```

**插件只负责第二段。** 第三段完全由主题掌握。

### 实测：VSCode 内置浅色主题的映射

直接解析 `resources/app/extensions/theme-defaults/themes/*.json`（本机 VSCode，2026-11-08）：

| scope | Visual Studio Light | Light+ |
|---|---|---|
| `keyword.control.verilog`（`always` `if`） | **#0000ff** | **#0000ff** |
| `keyword.other.block.verilog`（`begin` `end`） | **#0000ff** | **#0000ff** |
| `keyword.other.edge.verilog`（`posedge`） | #0000ff | #0000ff |
| `storage.type.verilog`（`input` `reg` `wire`） | **#0000ff** | **#0000ff** |
| `storage.modifier.verilog`（`parameter`） | **#0000ff** | **#0000ff** |
| `entity.name.type.module.verilog`（模块名） | 无规则（黑） | #267f99 青 |
| `constant.numeric.verilog`（`1'b0`） | #098658 绿 | #098658 绿 |

**结论**：两个内置浅色主题里都**没有 `keyword.control` 的独立规则**，只有笼统的 `keyword → #0000ff`。
所以无论插件把 scope 拆成 4 类还是 40 类，屏幕上都是同一种蓝。

> 顺带纠正一个错误判断：曾经怀疑是"其他 HDL 扩展抢了 grammar"。
> 用 `--disable-extensions` 干净环境复验后**颜色没有变化**，该假设被推翻。
> `test/grammar/dump.js` 也证明我们的 grammar 产出的 scope 完全正确。

### 因此本插件自带默认配色

`package.json` 的 `contributes.configurationDefaults` 里带了 17 条 `textMateRules`，
不依赖主题即可分出紫 / 蓝 / 青 / 绿 / 褐。用户自己的 `editor.tokenColorCustomizations`
优先级更高，想覆盖随时可以。

**实测线索**：拆分后 `module`(keyword.other.module) / `input`(storage.type) /
`begin`(keyword.other.block) / `always`(keyword.control) 四种不同 scope 仍然同色
→ 说明当前主题把它们抹平了。

常见的两套内置主题差别就在这里：

| 主题 | 表现 |
|---|---|
| **Light Modern / Dark Modern**（VSCode 1.7x 起的默认） | 关键字类基本统一成一种蓝，整体更"扁平" |
| **Light+ / Dark+**（原版 "Visual Studio" 主题） | 控制关键字紫、类型与块蓝、实体名青，层次更分明 |

参考图的效果更接近 **Light+ / Dark+** 或第三方主题。

## 2. 确定性解法：把配色显式写进设置

不想换主题、或想精确控制某个词的颜色，把下面这段贴进
**用户 `settings.json`**（`Ctrl+Shift+P` → `Preferences: Open User Settings (JSON)`）。

> 这份清单由 `package.json` 的 `configurationDefaults` 自动生成（build 0.3.2），
> 与插件内置配色完全一致；不贴也行 —— 插件已经自带同样的默认值。

## 3. 为什么之前没这么干，现在干了

原方案是"插件只把 scope 分对，颜色交给主题"，理由是换主题时颜色能跟着变。

**实测发现行不通**：内置浅色主题对 `keyword.control` 没有独立规则，
拆多少 scope 都是一种蓝。所以改为**插件自带一份默认配色**（`configurationDefaults`）。

代价与边界：

| 项 | 说明 |
|---|---|
| 主题换了颜色不跟着变 | 是有意为之 —— 默认色只覆盖本插件自己的 scope，不动别的语言 |
| 深色主题下对比度 | 默认给的是浅色主题配色；深色主题请按 §2 的深色列覆盖 |
| 用户想改 | 用户自己的 `editor.tokenColorCustomizations` 优先级更高，直接覆盖即可 |

## 4. 参考图里有一件事我们做不到

参考图 2 里 `vld_d`、`sh_period` 这些**标识符也有颜色**，而 `clk`、`rst_n` 是黑的。

那属于 **semantic tokens（语义着色）** —— 需要知道"这个名字是信号、端口还是参数"。
TextMate grammar 是纯正则，没有符号表。要那种效果，得等 S3a/S3b 的模块头解析 +
索引做完之后，把解析结果作为 `SemanticTokensProvider` 提供给编辑器。
